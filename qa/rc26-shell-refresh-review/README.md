## Pre-freeze deadline counterexample

`deadline-counterexample.cjs` loads the actual moving `sw.js` and runs `refreshKnownAppShell()` against a deliberately delayed atomic cache batch. Its result records the exact worker hash. This is a specification-conforming VM timing model, not native Cache API or hosted behavior proof.

The worker returns `{ok:false, code:'timeout'}`; a second request returns the same coalesced timeout with only one 41-request batch. The delayed complete batch then commits despite every `Request.signal` being aborted. The coalescing latch successfully prevents overlap. It cannot prove that every timeout preserves the previous bytes or that underlying network work is cancelled.

The [W3C Cache.addAll algorithm](https://w3c.github.io/ServiceWorker/#cache-addAll) invokes internal fetching for each constructed request. It does not specify hooking the supplied Request object's abort signal as the high-level `fetch()` method does. Once all response bodies finish, it starts [Batch Cache Operations](https://w3c.github.io/ServiceWorker/#batch-cache-operations), which has an atomic mutation/rollback contract but no abort-signal parameter. A response deadline and the cache transaction's outcome are therefore distinct.

The implementation owner was notified before freezing. Its `../rc26-update-multiclient/cache-addall-abort-native-results.json` now records a fresh owned Chrome 154.0.8037.58 experiment: when a response was still pending, aborting the Request signal caused `AbortError`, and the cached `old` bytes survived. Immediate physical/virtual memory floors passed and the owned browser/server closed. This current native evidence discriminates fetch-phase cancellation from the independent post-fetch commit model above. The platform/spec interpretation alone is not used to claim Chrome failed cancellation.

The coordinator explicitly accepted the narrow outcome contract: failed/unsupported/timed-out refresh never destructively clears shell caches or unregisters the worker and never automatically reloads; a rejected atomic batch leaves previous contents intact; a complete batch already committed or pending commitment may become visible after a caller's response deadline. Literal byte preservation on every timeout would require a larger staging/pointer design and is not established by this implementation. Existing actual and local force-reset failures in `../rc26-pc-update-qualification/` and `../rc26-update-multiclient/` remain unchanged.
