# Same-player head/tail reuse compared with local suffix reuse

Read-only design comparison, not implementation or a performance claim. Fixed rc31 uses a fresh source reader for each same-player seek (`ts-player.mjs:18–20,121–132`) and a new probe-local cache (`ts-seek.mjs:25,203–207`). For a source larger than one sample, head and tail are distinct mandatory reads on every probe. rc19 reuses them only for that generation's bootstrap construction; it does not persist raw head/tail across generations.

Raw unchanged bytes can be separated from stale async output. A bounded same-player cache could retain only owned raw final head/tail sample copies and their exact admitted account/content/version/checksum tuple. A new generation first awaits previous source/worker/MSE cleanup, opens its fresh reader and matches that tuple. Each cached logical read still receives fresh pre/post metadata/current-owner/source/account/checksum validation from that new reader before bytes are released. The probe parser, target plan, bootstrap and worker remain new and generation-tagged. Old promises, callbacks, parsed plans, MSE state and output are never reused. This can preserve the existing pure probe's cache-release and separate-probe API contracts while the player/source admission layer supplies unchanged bytes.

Checksum absence→presence, informational version changes or any cache key mismatch invalidate/reject cache reuse and fall back to the existing fresh body read; they do not alone turn an unrelated version update into a content failure. Existing real content/permission/checksum drift and stale-account failures keep their existing failure behavior. Exact fresh pre/post checks must compare the cached tuple, not merely the fresh reader's opening snapshot. Late checksum upgrades cannot silently relabel old null-checksum byte entries. No TTL alone establishes content validity.

| Candidate | Supported reuse boundary | Maximum additional owned raw bytes | Lifecycle/maintenance cost | Expected effect, not measured |
|---|---|---:|---|---|
| Within-generation chosen suffix | Same admitted reader/generation, exact copied chosen suffix; only wholly covered logical reads initially | ≤1MiB, released at consumption/failure/retirement | Short lifetime; existing 503 reader-change fallback; partial coverage often cannot remove a whole body request | Potential duplicate body GET removal; metadata barriers stay |
| Same-player head/tail | New reader/generation freshly admits exact cached content tuple after old cleanup | ≤2MiB for final widest head/tail copies, independent of file size | Player-lifetime bytes, new source admission/metric/release semantics and stricter invalidation; clears on player disposal/identity change | Potential repeated head/tail body GET removal across seeks; metadata barriers stay |

Consolidate their ownership in one source-owned fenced admitted-byte read contract if either is adopted, rather than duplicate identity logic in the probe and player. Preserve ≤1MiB physical/logical read bounds, exact Range validation for fresh bodies, private cache/descriptor scope, current-owner checks, 188-byte sample boundaries, original video/audio/GOP preroll, 64KiB pushes/ACK and lifetime503 budget. Retained-byte metrics must distinguish real received bytes from cached copies/reuse; no fabricated transport counts.

The existing synthetic suffix proof establishes byte-equivalent bootstrap input/output only. A future same-player implementation would need byte-equal head/tail-derived plans and worker output across repeated seeks, cold/warm/EOF native target-frame and audio-preroll equivalence, plus drift/version/checksum upgrade/permission/account/cancellation/503/cleanup counterexamples. No such implementation or native cache proof exists yet. The actual original's offsets and whether the first target frame needs those particular requests are not exported in the old result, so there is no observed request saving, latency p95 gain or maintenance-free assertion.
