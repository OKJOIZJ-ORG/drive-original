# rc.31 finite prefix failure continuity — local preparation

This additive QA leaf is pinned to public Git
`4a484e6f839d2e6c3eb83503acb08147362cb011` / `1.22.0-rc.31`.
It does not change the product or the historical strict factories, runners,
preparations or actual results. `provenance.json` binds the exact producers;
`freeze.json` binds this complete local deliverable and every historical file
used by its build. No actual browser, network, account or device run was performed.

The original factory already exposes successful immutable entries after a
settled, catalog-stable partial file failure (`../rc31-corpus-content-continuity/probe.mjs`,
`probeFile`, final coverage/capsule creation and `continuity`). The original
runner's `tick` demands every file pass before requesting that capsule. On an
otherwise settled partial job it drops its active job without requesting the new
capsule. Historical redacted JSON proves scoped outcomes but cannot reconstruct
that private registry. This new evaluated factory starts a **fresh** registry;
it never imports old capsules or silently credits the historical 63 fresh file
successes from the failed strict second job. Preserve those results separately.

The new private capsule contains two separate bounded collections: admitted
immutable prefix records and an attempt ledger. Successful records are admitted
only after original exact Range/body validation and successful strong immutable
preflight/postflight checks, followed by a stable complete before/after catalog
and awaited release with no fatal failure. Failed prefix bytes never enter it.
Both collections are limited to 8192 unique files. Counts remain across idle
credential renewal and across representative/video phases; an exhausted ID is
not reset if it disappears and returns. No bytes, token, owner or resource key
are retained. Local Node exports support tests; the evaluated browser factory
only exposes creation and `clearContinuity`, with unforgeable WeakMap handles.

At most two fresh attempts per file are admitted in this registry. An extra
attempt requires a transient `POSTFLIGHT_FAILED`, `PREFLIGHT_FAILED`,
`HEADER_TIMEOUT`, `BODY_TIMEOUT` or `FILE_TIMEOUT`, a previously observed usable
immutable preflight tuple, unchanged current catalog identity, and a new strong
preflight tuple equal to that previous tuple. A failed preflight with no usable
baseline is exhausted after one attempt. Payload, protocol and other validation
failures are also exhausted without repeating the same read. Identity drift,
owner/source/catalog drift, cancellation, cleanup failure and limits are fatal.
Transient errors receive no retry inside their failed job: the next explicitly
authorized finite burst/job captures a fresh owner and full catalog and reads a
fresh prefix within the unchanged budgets. Retry candidates precede new files.

Coverage partitions remain `classified + failed + ineligible + unattempted =
denominator`. `failed = retryPending + retryExhausted`, `queuedFresh = unattempted`,
`queuedRetries = retryPending`, and `queuedTotal = queuedFresh + queuedRetries`.
`complete` only means the bounded cohort settled with reconciled dispositions.
The runner advances an opaque partial capsule only with `complete`, `catalogStable`,
`released`, no fatal failure and internally consistent counters. Exhausted files
stay failed and unvalidated. `progressExhausted` with failed files ends the queue
without claiming `eligibleVideoPrefixesComplete`; only failed0 and unattempted0
after the current final catalog can qualify eligible prefix completion.
`wholeCorpusComplete` always stays false: 940-byte signatures do not establish
deeper metadata, codecs, tracks, playback, audio or physical-device behavior.

Original fences and limits remain: exact authenticated current-owner readonly
runtime; projection/writer/playback/retirement/source/controller/foreground
checks; four inventory passes/job and final-inventory reserve; <=64 files/job in
serial sub-batches of8; 512 metadata GETs/64MiB/600s per job; 50s and64 requests/
2MiB+8192 bytes per file; 1MiB/request; 10s headers/no-progress and 10s file metadata;
25s default inventory metadata. No whole-file GET or media continuation. The
public rc.31 account-state JSON reader's 30s deadline governs a different product
read owner and is not a reason to raise this independent QA metadata deadline.
Generic upstream cleanup remains unknown. Safe runner output only retains
whitelisted counters, failure codes, kinds and MIME/extension bins; private keys
and values are excluded. Unrecognized bins are omitted, not renamed into proof.

Root first closes/removes the old corpus runtime and qualifies actual served31,
current activated proof, visible idle playback, idle state writer and current
context. Reuse the exact existing rc.31 `sw-proof.expression.js` and
`derive-context.expression.js` preparations, freshly qualified by root; never
print the context. Evaluate this leaf's `runner.expression.js` once, retain the
installer privately under new names such as `__rc31PrefixRecoveryInstall` and
`__rc31PrefixRecoveryRunner`, and install using the four-field private context
and current proof. The installer takes no factory, capsule or saved JSON input.

There is no automatic start. For each explicit `start`, root independently
qualifies fresh token expiry/natural-watch cutoff and cleanup margin, then
supplies `{maxJobs, deadlineMs, stopBeforeAt}` with <=8 jobs, <=80 minutes and a
fresh cutoff strictly before those boundaries. The first phase is representatives
<=36; it continues until its queued count is0, then videos<=64. Read only safe
`runner.read()` output. Idle successful/partial bursts may continue with a fresh
explicit start after renewal if the context's drive generation still matches.
Active owner changes, deadline, pause, cancel or fatal failure remain terminal.
Exhausted complete queues cannot restart to bypass the attempt limit. Root saves
safe evidence before explicit `cleanup()` and waits for `disposed`/no active job
before deleting the privately held installer, runner, context and proof helpers.
No automation, outer retry loop or runtime recovery from exported JSON is supplied.
