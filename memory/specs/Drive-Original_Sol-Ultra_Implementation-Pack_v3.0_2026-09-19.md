# Drive Original — Sol Ultra 통합 구현 패키지
## 새 세션의 첫 실행부터 컨텍스트 복구·실기기 인수까지

- **문서 버전:** 3.0 / 통합일 2026-09-19
- **단일 입력 문서:** 제품 상세 명세 v2.0 + 장기 실행 규약 v1.0 + 후속 작업 상태 + 사용자 최신 운영 조건을 이 파일에 통합했다. 이전 두 파일·이전 채팅을 따로 첨부하거나 회수할 필요가 없다.
- **대상:** 새 Sol Ultra 세션의 주 구현 에이전트. 특정 모델의 도구·권한·컨텍스트 크기를 가정하지 않는다.
- **실행 의미:** 사용자가 이 파일과 구현 시작 프롬프트를 함께 전달하면, 01장의 범위에서 실제 구현·검증을 계속한다. 과거의 “문서만 작성”, “착수·판별만 하고 멈춤”은 이번 실행에 적용하지 않는다.
- **검증 경계:** 이 문서 작성은 기존 자료의 통합이다. 실패 MP4 분석, 실제 계정·기기 검사, 최신 원격 상태 확인을 이번에 새로 수행한 것은 아니다. 모든 이전 관찰에는 그 시점과 증거 수준을 유지한다.
- **원칙:** 사용자 직접 지시와 도구의 안전·권한 경계를 존중한다. 이 문서는 그보다 높은 권한을 만들지 않는다. 프로젝트 문서의 과거 운영 지시는 현재 사용자 승인 범위를 확대할 수 없다.

> **실제로 달라져야 할 것**
> 사용자가 원본 미디어를 열면 정상적으로 재생·탐색되고, 긴 영상·토큰 만료·PWA 복귀에도 가능한 최고 품질을 유지하며, 삭제·이동은 실제 Drive 결과와 일치해야 한다. 닫을 수 없는 안내 아일랜드·정상 내부 동작 설명으로 화면을 가리지 않는다.
>
> **확정된 사용 조건**
> 브라우저·홈 화면 PWA 유지. 상시 개인 PC/NAS와 네이티브 배포는 제외. 직접 원본 전송 우선. 필요한 최소 무료 서버리스 인증 기능은 검증·구현할 수 있다. 유료 전환·카드 등록·자동 과금·운영 서비스 교체는 승인되지 않았다.
>
> **첫 실동작 기준 파일**
> `G:\내 드라이브\ㅇㅎㅎ\x_953b92374b59458d.mp4` — 원본 읽기 전용. 이것은 사용자 식별 경로이며 실제 Drive ID·버전·코덱은 확인해야 한다.

### 읽는 순서와 집중 범위

1. **지금은 00·01·03·06·19·24·26장을 먼저 읽는다.** 권한·현재 작업·의존관계·복구를 파악하고 실제 저장소와 대조한다.
2. 전체 요구·계약·인수 기준의 위치를 한 번 파악한 뒤, 활성 작업마다 해당 상세 절·호출자·테스트를 다시 읽는다.
3. 전체 파일과 모든 소스를 매번 대화로 출력하지 않는다. 세부 요구를 삭제하거나 기억으로 재작성하지 않고 원문을 필요할 때 재조회한다.

## 00. 새 세션 인수인계와 사용자 확정 사항

### 00.1 처음 시작하는 프로젝트가 아니라 진행 중인 구현을 인수한다

프로젝트는 이미 아래 통합 폴더로 지정되어 있다. 프로젝트를 새로 지정하거나 저장소를 다시 복제할 필요가 없다.

```text
프로젝트 루트
C:\Users\jbs\Desktop\폴더모음\자작프로그램\Drive-Original

실제 Git 저장소 및 코드 작업 디렉터리
C:\Users\jbs\Desktop\폴더모음\자작프로그램\Drive-Original\source

실패 표본
G:\내 드라이브\ㅇㅎㅎ\x_953b92374b59458d.mp4
```

아래는 **직전 워커 보고와 당시 인수인계 자료**다. 새 세션이 현재 상태라고 강제 적용해서는 안 된다.

| 항목 | 마지막으로 제공된 값 | 새 세션의 처리 |
|---|---|---|
| 작업 브랜치 | `codex/v2-kickoff-diagnostics` | 실제 브랜치·동시 작업·dirty 상태를 확인 후 이어받음 |
| 작업 커밋 | `a804e07423479eefa5413c670fc1f62e21d68cf3` | 문서·진단 실행계획 커밋. 제품 수정 완료 SHA가 아님 |
| 미커밋 상태 | `memory/CHECKPOINT.md`의 커밋 후 참조 갱신 하나라고 보고됨 | 지금도 같은지 확인. 삭제·덮어쓰기 금지 |
| 제품 기준 | v1.21.0 / runtime `e08989a6caecc51bc2fdd37f538619fa8ed5900d` | 이후 변경 및 실제 앱/서비스 워커 버전 재확인 |

이전 소스와 기록이 이후 바뀌었다면 현재 상태를 우선 관찰하고, 사용자 변경·다른 워커 변경을 보존한다. **다른 세션이 같은 파일을 실제 수정 중이면 편집 소유권을 먼저 확인한다.** 파일 잠금 충돌을 피한다는 이유로 사용자 프로세스를 임의 종료하거나 작업을 삭제하지 않는다.

### 00.2 사용자가 제공한 재현 조건

- 정확한 실패 표본 중 하나는 위 MP4다. 아직 코덱·컨테이너 내용·실제 file ID는 검증되지 않았다.
- PC 브라우저와 iPhone Chrome 탭에서는 앱의 원본 경로 대신 Google Drive 호환 플레이어로 넘어가는 현상을 보고했다. **호환 플레이어에서 영상이 실제로 재생 완료됐다는 보고는 아니다.**
- 사용자가 “iPhone Chrome에서 설치한 PWA”라고 부르는 홈 화면 실행에서는 Google 계정 접근 불가, 로그인 또는 쿠키 허용 안내가 표시된다고 했다.
- Google 도움말 서명: `https://support.google.com/drive/answer/13812413?hl=ko`.
- 사용자는 PWA 내부에서 쿠키 허용 메뉴를 찾지 못했고, 브라우저로 간단하게 쓰기를 원한다.
- PC 브라우저 종류, iPhone/iOS 버전, 실제 standalone 모드와 최초 실패 계층은 아직 미확인이다. 도구로 확인할 수 있는 것은 직접 확인한다.
- 홈 화면에 추가한 브라우저 이름만으로 저장소 공유·엔진·쿠키 정책을 확정하지 않는다. 다른 환경의 차이와 원본 경로 최초 실패를 분리한다.

과거 스크린샷이 새 세션에 없더라도 이 텍스트와 실제 표본으로 착수할 수 있다. 실제 시각 판정에 필요한 추가 화면만 요청한다. 원문이 회수되지 않은 이전 ChatGPT 대화에 설계를 종속시키지 않는다.

### 00.3 운영 형태와 권한에 대한 확정 입력

| 사용자 조건 | 구현에 적용할 의미 |
|---|---|
| 상시 Windows PC/NAS 없음 | 개발 PC는 일시적 실험에만 사용. 운영 서버 전원 의존성 도입 금지 |
| 소유한 클라우드 자원은 사실상 Google Drive뿐 | Drive는 미디어 저장소. 실행 호스트가 이미 마련됐다고 가정하지 않음 |
| 브라우저·PWA로 간단하게 사용 | 네이티브 앱·서명·앱스토어·외부 VLC 전환을 정상 이용의 필수 단계로 만들지 않음 |
| 새 HTTPS origin/OAuth client 이관 허용 | 최소 필요 변경 및 비파괴 이관 가능. 기존 state 보존·복구 필요 |
| 일회용 테스트 데이터 쓰기 허용 | 이번 실행이 만든 테스트 폴더/ID만 이동·휴지통·복원 가능. 실제 원본은 읽기 전용 |
| 실제 기기 테스트에 바로 참여 가능하다고 답함 | 후보가 준비되면 짧은 구체적 절차로 요청. 도구의 iPhone 자동 제어 권한을 뜻하지 않음 |

본인 로그인·2단계 인증·서비스 계정 생성·경로 접근 승인처럼 실제 사용자 동작이 필요할 수 있다. 이것은 설계를 사용자에게 다시 떠넘기는 사유가 아니다. **필요한 동작 하나와 목적·비용·확인 결과만 알려 주고, 나머지 진행 가능한 작업은 계속한다.** 장시간 대화가 지나면 사용자가 계속 대기하고 있다고 추정하지 않는다.

### 00.4 이번 방향: A와 B를 책임별로 나눈다

**기본 사용 경로는 브라우저/PWA. 원본 데이터는 직접 전송을 우선한다. 반복 인증 문제에는 필요한 최소 무료 서버리스 인증 계층(B-auth)을 우선 검증한다.**

- A: 현행 PWA/SW/직접 reader의 원본 전송·수명주기 결함을 먼저 재현·수정한다.
- B-auth: 적합한 code/offline access·서버 보관 refresh token·앱 세션으로 인증을 보완하는 작은 제어 계층. 실제 필요성과 무료 운영·보안·이관을 검증한 뒤 통합한다.
- B-media: 영상 바이트 중계. B-auth를 쓴다고 자동 도입하지 않는다. 실제 직접 경로 문제를 해결하는 경우에만 추가한다.
- Q1/Q2/Q3: 파일과 기기에 따른 미디어 처리 계획. B-auth의 존재와 동등한 개념이 아니다.
- C: 사용자 정상 사용을 위한 네이티브 앱 배포는 이번 범위에서 제외한다. 로컬 네이티브 도구는 읽기 전용 비교 실험에 사용 가능하다.

인증 구조의 채택은 영상 reader 속도 비교에만 종속되지 않는다. 로그인 수명주기 개선이 독립적인 채택 근거다. 반대로 실패 MP4가 재생된다는 이유만으로 장기 인증 문제가 해결됐다고 판정하지 않는다.

### 00.5 기존 BLOCKED 항목을 이렇게 해소한다

- `A-005`: 사용자 식별 경로·재현 환경은 제공됨. 실제 Drive ID·버전·trace·원인은 확인 전까지 미확인으로 유지한다.
- `A-006`: 운영 선호를 다시 물을 필요 없음. 브라우저/PWA·무상시 개인서버·조건부 무료 서버리스·origin/OAuth 이관 허용을 반영한다. 서비스 계정·실제 한도·비용 적합성은 별도 확인한다.
- `A-007`: 01·13장의 일회용 테스트 범위로 승인됨. 실제 로그인·scope·도구 접근이 남으면 그 구체적 장애만 표시한다.
- `V2-02A/B`의 “착수만 허용” 차단은 해제한다. UI와 장황한 정상 문구는 전송 실험의 완료에 불필요하게 종속시키지 않는다.
- “READY 하나”는 **동시 핵심 편집 하나**라는 운영 규칙이지, 첫 작업 후 영구 정지 지시가 아니다.

계획의 표·의존도·상단 완료 정의·OPEN-QUESTIONS·체크포인트를 함께 정렬한다. 과거 “OPFS 우선”·“자동 Google fallback” 같은 지침이 목표 상단에 남아 있다면 현재 원본 streaming·수동 외부열기 계약과 충돌하는 부분만 명시적으로 supersede한다. 이력은 보존하되 오래된 문장이 현재 실행을 다시 지배하게 두지 않는다.

### 00.6 도구와 입력 경로

1. 첨부 원문을 실제로 읽고 전체 파일 접근이 가능한지 확인한다. 미리보기 몇 줄만으로 구현을 시작하지 않는다.
2. 필요하면 이 통합 문서 **한 부만** 기존 `memory/`의 명세 소유 위치에 원문 그대로 저장하고 해시·위치를 기존 인덱스/goal에 연결한다. 적절한 기존 위치가 없으면 `memory/specs/`를 사용할 수 있다. 기존 두 원문은 이력으로 보존한다.
3. 현재 작업 상태는 goal·CHECKPOINT가 소유한다. 이 입력 문서를 매 단계 복제해 새로운 상태판으로 쓰지 않는다.
4. 앞 세션에서는 전용 파일 읽기 도구가 `G:` 경로를 승인 루트 밖이라고 거부한 적이 있다. 현재도 그렇다면 허용된 커넥터/API 또는 사용자 경로 승인으로 해결한다. 우회·권한 상승·숨겨진 마운트 변경은 하지 않는다.
5. 이름 검색은 후보 찾기다. 부모·계정·크기·시각 등으로 동일 파일을 검증하지 않고 첫 검색 결과를 선택하지 않는다.
6. 실제 제공되지 않는 도구·플러그인·Ballast skill·특정 CLI를 필수로 가정하지 않는다. 사용할 수 있는 정상 도구로 같은 정보 소유권·실행·재조회 규칙을 지킨다.

## 01. 권한·요구 해석·완료 정의

### 01.1 원래 목적을 축소하지 않는다

목적은 Drive Original의 앱 내부 경험 개선이다. 외부 VLC에서만 재생되는 결과, Google iframe으로 넘긴 결과, MP4 한 개 또는 mock 테스트만 통과한 결과로 전체 요구를 닫지 않는다. 원본 직접 재생·품질 보존·실제 Drive 작업·조용한 UI와 11개 확장자 대상의 지원 요구를 유지한다.

여러 단계·컨텍스트에 걸쳐 실제 구현한다. 기술·계약·인수 기준보다 더 단순하고 확실한 구현이 있으면 사용자 요구와 안전장치를 보존하면서 채택하고 이유를 남긴다. 모든 가능한 환경의 무결점을 보장하거나 테스트 범위를 과장하지 않는다.

### 01.2 이 문서와 시작 프롬프트로 승인하는 구현 범위

| 행동 | 허용 범위와 조건 |
|---|---|
| 로컬 개발 | 현재 작업 브랜치의 제품 소스·tests·qa·필요 문서 수정, 프로젝트 범위 의존성/개발 도구 준비, 비파괴 표본 분석, 로컬 테스트·리뷰 가능한 커밋 |
| 실패 표본·코퍼스 | 지정 표본 읽기, bounded probe와 필요한 원본 구간 조회, 비공개 파생 실험. 원본 덮어쓰기·전수 hydration/변환 금지 |
| 테스트 Drive 쓰기 | 이번 작업이 생성한 고유 테스트 폴더·작은 파일의 생성·이동·휴지통·복구·원격 재조회·잔여 정리. 실제 원본/기존 사용자 폴더 제외 |
| 인증 설정 | 이 앱에 필요한 HTTPS 후보 origin/OAuth client 구성과 비파괴 상태 이관. 기존 프로젝트·앱 정체성 우선 재사용. 변경 전 상태·복구 계획 기록 |
| 무료 서버리스 | 카드·자동 과금·유료 계약 없이 가능한 최소 인증/필요 API의 개발·계정 허용 범위 설정·검증용 배포. 무료 한도·정책·실제 사용량 확인 |
| 실제 기기 | PC와 사용자 iPhone의 검증 가능한 후보 제공. 사용자에게 본인 조작 2~3단계만 요청. 자동 제어 가능하다고 추정하지 않음 |
| 저장소 기록 | goal·결정·체크포인트·증거의 정상 소유 문서 현행화. 외부 Notion이나 별도 자동화 시스템은 이번 범위 아님 |

안전한 후보 배포 권한은 **사용자 미디어·기록·비밀을 공개할 권한이 아니다.** 새 주소에 공개되는 것은 검토된 앱 shell과 권한 검사된 endpoint뿐이다. 개인 데이터·진단·credential은 공개 build/로그/응답에서 제외한다.

기존 앱 state의 읽기·검증된 신규 state 전송은 허용하지만, 기존 appData/legacy writer 원본 삭제나 빈 상태 덮어쓰기는 금지한다. 이것은 미디어 테스트 쓰기 허용 범위와 별개의 비파괴 이관 권한이다.

### 01.3 승인되지 않은 행동과 사용자 본인 조작

- `main` 병합, 원격 push, 기존 production 서비스 교체/전환 배포는 최종 후보를 준비한 뒤 별도 승인 대상으로 남긴다. 검증용 배포와 구분한다.
- 유료 플랜·카드 등록·자동 과금·도메인 구매·상시 PC/NAS 운영·네이티브 앱 배포는 하지 않는다. 무료 한도가 부족하면 조용히 유료 전환하지 않는다.
- 실제 라이브러리 이동/휴지통/삭제/변환, 원본 공개 공유, 영구 삭제, 전체 휴지통 비우기는 하지 않는다.
- 다른 앱의 OAuth·계정·브라우저 쿠키·캐시를 변경하거나 Google 계정 전체 권한을 철회하지 않는다.
- `reset --hard`, `git clean`, force push 등으로 기존 작업·이력을 지우지 않는다. 사용자 프로세스·서비스를 임의 종료하지 않는다.
- 중지된 자동화, 이전 Antigravity 작업, 별도 앱 운영 작업을 재개하지 않는다.
- 새 계정 가입·로그인·2단계 인증·동의 화면처럼 본인 행동이 필요한 경우 그것만 구체적으로 요청한다. 비밀번호·토큰·쿠키 원문을 채팅에 보내라고 하지 않는다. 약관·결제에 대신 동의하지 않는다.

도구가 개별 작업에 별도 승인을 요구하면 정상 승인 경로를 따른다. 문서의 일반 구현 허용을 이유로 그 안전장치를 우회하지 않는다. 한 분기의 접근/비용이 차단됐다고 승인된 다른 READY 작업까지 멈추지 않는다.

### 01.4 완료와 승인 대기

1. BUG-01~08 및 직접 관련 추가 결함에 재현·수정·회귀 증거가 연결된다.
2. 명시 표본과 11개 확장자/실제 codec 조합의 원본 우선 경로를 구현·검증한다. 미확인·미지원·손상을 구분한다.
3. 장기 인증·느린 전송·쿠키 제한·부분 쓰기 실패에서 계정 혼합·데이터 유실·가짜 성공·무한 루프가 없다.
4. 실제 Google·iPhone·승인된 파일 쓰기의 인수 결과를 기록한다. 기기 접근이 없으면 해당 항목만 BLOCKED로 두며 최종 인수 완료로 승격하지 않는다.
5. 이번 실행의 종료점은 **검증된 후보 + 고정 소스 상태 + 남은 live gate + 운영 전환 승인 요청**이다. `G6`는 별도 운영 배포 승인 대기로 남길 수 있다.

“구현 완료”, “로컬 테스트 통과”, “실제 인수 완료”, “운영 배포 완료”는 네 가지 다른 주장이다. 가능한 작업은 끝까지 진행하고 결과로 보고하되, 원래 요구를 낮춰 완료 상태를 만들지 않는다.

### 04.2 첨부 이미지에서 확인되는 것

사용자가 제공한 이미지에는 Google 호환 재생 표시, 닫기 버튼, `Google 계정에 액세스 할 수 없습니다`라는 Google 페이지, 로그인/쿠키 접근 안내, 하단 `원본 다시 시도`·`Drive 직접 열기` 패널이 보인다.

확인되는 것은 **원본 경로 대신 Google 문서가 열렸고, 그 문서가 계정/쿠키 접근 오류를 표시했다는 것**이다. 원본 전송 최초 실패 원인·API 토큰 만료·실행 앱 버전·정확한 Safari/PWA 모드는 이미지 하나로 확정할 수 없다.

참조 이미지가 워커에게 첨부되지 않았더라도 위 실패 서명으로 명세를 이해할 수 있어야 한다. 실제 시각 재현 판정에는 원본 이미지 또는 새 화면 기록을 사용한다.

| ffmpeg.wasm | 브라우저의 FFmpeg 기반 처리 | 작고 제한된 파일의 보조 실험 | 조사한 FAQ에 큰 입력·성능 제약. 4 GiB 이상의 개인 영상 전체를 메모리에 올리는 기본 설계에서 제외 [R31] |
| GoogleDriveM3U | 공개 접근 링크로 재생 목록 구성 | 본 프로젝트의 기본 경로로 채택하지 않음 | 읽은 설명은 누구나 링크로 접근 가능한 공유를 요구하므로 비공개 원본 보존 요구와 불일치 [R33] |

### 05.3 실제 코드 읽기에서 발견한 재사용 제외 사항

OpenList의 이번에 조회된 Google Drive 드라이버 구현에서는 다음 동작을 확인했다. **이것은 읽은 구현 응답에 대한 관찰이며, 모든 릴리스나 프로젝트 전체의 평가가 아니다.** [R26][R27]

- `Link`가 `alt=media`와 Authorization 헤더를 분리해 제공하는 형태는 구조 참고가 된다.
- 같은 구현의 링크에는 `acknowledgeAbuse=true`가 자동 포함된다. **본 앱에서는 복사하지 않는다.** 보안 경고를 무조건 자동 승인해서는 안 된다.
- `Remove`가 HTTP DELETE를 사용하는 구현은 본 앱의 기본 휴지통 이동 계약과 다르다. **파일 작업 코드를 그대로 가져오지 않는다.**
- `Move`의 이전 부모 처리도 현재 원격 부모를 확인하는 본 명세와 다르다. 동일 이름의 API가 있어도 의미가 같다고 가정하지 않는다.
- 외부 서비스에 refresh token을 넘기는 편의 경로는 본 앱의 기본 인증 구조에서 제외한다. 사용자 소유 OAuth/토큰 보관 경로를 사용한다.

즉 “오픈소스를 가져오기”의 기본 단위는 **검증된 인터페이스·알고리즘·라이브러리**이며, 검토되지 않은 드라이버 전체 덮어쓰기가 아니다.

### 05.4 2026년 자료에서 재확인한 운영 위험

rclone 공식 Drive 문서와 유지관리자 공지는 공용 client ID의 2026년 중단 예정과 자체 ID 사용 필요를 안내한다. 이미 중단됐다고 단정하거나 정확한 중단일을 만들어내지 않는다. 새 구조는 공용 ID를 기본 의존성으로 설계하지 않는다. [R19][R22]

Google Drive의 사용량 정책도 고정된 옛 요청 수/영구 무료 가정을 사용하지 않는다. 조사한 공식 문서는 quota unit과 향후 과금 변경을 안내한다. **실제 사용자 프로젝트의 적용 한도·공지·과금 여부를 실행 시 확인**하고, 무제한 병렬 다운로드나 15초마다 전체 드라이브 스캔을 만들지 않는다. 본 문서에는 확인되지 않은 월 이용료를 제시하지 않는다. [R13]

### 05.5 현재 재사용 권고

- **기본 개념 채택:** Jellyfin식 품질·호환성 경로 구분, 계정별 단일 인증 소유자, 구간 전송·취소·제한 캐시.
- **우선 실험:** 공식 Drive API reader와 rclone의 읽기 전용 비교. 실제 코덱 문제가 확인되면 네이티브 FFmpeg 재포장 또는 libVLC 비교.
- **조건부 런타임 채택:** 브라우저/PWA와 최소 인증 서비스에 실제 필요한 Google 공식 인증 라이브러리·브라우저 분석/재포장 도구·필요할 때 hls.js. FFmpeg/native는 로컬 판별 도구부터 활용하며 서버리스에 native 실행 환경이 있다고 가정하지 않는다. 불필요한 전체 앱 프레임워크 추가 금지.
- **기본안 제외:** Google iframe 자동 fallback, 원본 공개 링크, 제3자 토큰 중계, 브라우저 대용량 전체 변환, 수천 파일 일괄 변환 선행.
- **결정 유예:** 최소 서버리스 서비스·저장 방식·인증 인터페이스·필요한 브라우저 처리 모듈·캐시 크기. 네이티브 배포와 상시 개인서버는 이번 후보에서 제외됐다. 세부값은 실제 실험과 유지보수 비용으로 선택한다.

## 06. 브라우저 유지·직접 전송·최소 인증 계층의 구조 결정

### ARCH-01 — 결정된 사용 형태와 아직 검증할 구현을 구분한다

| 구성 | 현재 지위 | 채택 근거 / 제외 경계 |
|---|---|---|
| A. PWA + 직접 원본 전송 | 기본 데이터 경로 | 현행 token/SW/Range/수명주기의 실제 결함을 고치고 원본 직접 재생을 유지 |
| B-auth. 무료 최소 인증/필요 제어 API | 우선 검증·구현 후보 | 장기 갱신·앱 세션·기존 state 이관의 실제 이익과 무료 운영·보안 적합성을 검증 |
| B-media. 원본 바이트 중계 | 조건부 보조 경로 | 직접 경로의 실제 장애를 해결할 때만. B-auth 채택의 자동 결과 아님 |
| Q1/Q2/필요 Q3 처리 | 파일별 계획 | 원본 stream 보존 우선, 실제 client·실행 자원·seek 증거 필요 |
| 상시 개인 PC/NAS·일반 FFmpeg 서버 | 이번 기본안에서 제외 | 사용자 가용성·운영 조건과 불일치 |
| C. 사용자용 네이티브 설치/배포 | 이번 범위에서 제외 | 로컬 판별 도구는 가능하나 앱스토어·서명·외부 VLC를 정상 경로로 강요하지 않음 |

단일 큰 B를 “인증 개선 + 영상 중계 + 디스크 캐시 + 재인코딩” 패키지로 만들지 않는다. 인증 문제의 해결 필요와 미디어 문제의 해결 필요는 각각 판단한다. 목표는 가능한 모든 기술 추가가 아니라, 운영 제약 안에서 가장 적은 책임 이동으로 실제 문제를 해결하는 것이다.

기존 방식으로 동일한 장기 세션 요구를 실제 충족하는 더 단순한 정상 경로가 확인되면 재사용할 수 있다. 단, GIS timer를 늘리거나 만료를 무시하는 방식은 그 증거가 아니다. [R01][R02][R03]

### ARCH-02 — 우선 검증할 B-auth + 직접 데이터 경로

```text
PC / iPhone Chrome·Safari / 홈 화면 PWA
    ├─ 같은 HTTPS origin: 정적 앱 shell + 최소 인증/API
    │      ├─ 앱 세션·Google OAuth code exchange
    │      ├─ refresh token의 서버 보관·계정별 갱신 조정
    │      ├─ 기존 appData 접근/이관 확인
    │      └─ 필요한 경우 단일 operation 제어 계층
    │
    └─ 데이터 경로: 검증된 앱/SW/source reader → 공식 Drive API
           ├─ 원본 구간 전송, first frame, seek
           └─ 필요 파일의 제한된 client-side probe/remux

[증거가 있을 때만] 같은 앱 origin의 media relay를 데이터 경로에 추가
```

B-auth가 브라우저 직접 Drive 접근용 access token을 전달해야 한다면, 인증된 앱 세션에만 짧은 credential을 제공하고 메모리 사용을 기본으로 한다. `no-store`, 정확한 Origin/CSRF 검사, 세션·계정 revision, 로그 정제, cross-account 거부를 갖춘다. refresh token·client secret은 브라우저에 주지 않는다. API 응답이 공개 캐시나 SW shell cache에 들어가면 안 된다.

프런트에 짧은 token을 주지 않고 필요한 API 호출만 같은 origin으로 대리하는 구성도 비교할 수 있다. 어느 쪽을 채택하든 토큰 갱신의 소유자는 하나이고, 브라우저/SW/서비스가 서로 갱신하며 경쟁하지 않는다. 직접 미디어를 위해 SW가 필요하면 데이터 전달 역할은 남길 수 있다. B-auth를 도입했다는 이유로 SW 전체를 삭제하지 않는다.

### ARCH-03 — 무료 서비스 선택과 운영 전제

Cloudflare Workers처럼 정적 자산과 작은 API를 제공하는 서비스를 **우선 확인할 후보**로 둔다. 구현 시 해당 공식 문서·계정·약관·요금제·저장 수단을 확인한다. 이 문서는 특정 무료 한도나 native FFmpeg 지원을 보장하지 않는다. [I01][I02][I03]

선택 기록에는 최소 다음이 있어야 한다.

| 검증할 것 | 충족 조건 |
|---|---|
| 계정·설정 접근 | 실제 사용할 수 있거나 본인 조작만 남았음. 계정이 있다고 추정하지 않음 |
| 비용 | 카드·자동 과금·유료 계약 없이 사용 가능. 예상 요청·저장량과 한도 초과 행동 기록 |
| 가용성 | 개인 PC 전원과 무관. 일시 장애 시 현재 데이터 보존·명확한 재연결 |
| 저장 | refresh token·앱 세션을 안전하게 보관하고 필요한 동시성 확보 |
| 갱신 조정 | 메모리 변수/단일 인스턴스만으로 여러 실행 인스턴스의 동시성을 해결했다고 주장하지 않음 |
| origin·callback | 실제 iPhone 탭/PWA 로그인 복귀와 CSRF·세션 보호가 동작 |
| 미디어 | 릴레이가 없으면 영상 바이트를 서비스 요청량에 억지로 포함하지 않음. 있으면 CPU/메모리/streaming/정책 별도 검증 |
| 중단·철회 | 후보 endpoint·캐시·비밀의 소유 위치와 안전한 비활성화 경로 |

최종적 일관성 KV의 단순 read/write를 전역 원자적 잠금처럼 사용하지 않는다. 실제 플랫폼에서 보장하는 직렬화·트랜잭션·조정 수단 중 필요한 최소만 채택한다. 원자성을 가정하는 대신 동시 두 기기·두 요청·재시작 테스트로 확인한다. [I04]

이미 승인한 무료 후보 설정을 기술 선택마다 다시 승인받을 필요는 없다. **결제·카드·약관 동의·본인 인증·경로 접근처럼 실제 권한 경계가 있을 때만** 필요한 동작을 구체적으로 요청한다.

### ARCH-04 — 판별 실험과 조기 종료

**원본 데이터 경로**는 동일 파일·버전·구간에서 다음을 비교한다.

1. 현재 앱/SW의 credential→headers→first byte→frame trace.
2. 독립 공식 API reader의 시작/중간/끝 범위와 실제 bytes.
3. 전송이 정상인데 browser만 실패하면 로컬 네이티브 probe/재생으로 container/decoder 분리.
4. 필요한 표본만 원본을 건드리지 않는 Q1, 필요한 경우 Q2 실험.

**인증 경로**는 독립적으로 검증한다.

1. 실제 OAuth 설정·현재 인증 모델과 만료 행동.
2. 최소 code/offline access·앱 세션 후보의 보안·회복·PWA 복귀.
3. 기존 appData·origin 이관·동시 갱신·무료 운영 적합성.

원본 reader가 똑같이 재생된다는 이유로 인증 개선을 기각하지 않는다. 서버 reader가 성공한다는 이유로 영상 전체 중계를 필수로 만들지도 않는다.

아래 기록이면 채택한 하위 경로를 구현한다. 같은 근거로 아키텍처 탐색을 무한 반복하지 않는다.

```text
채택한 auth owner / data path / operation owner
해결할 사용자 문제와 판별 증거
기각·보류한 접근과 이유
실제 사용자 추가 동작·무료 운영 조건
기존 state 이관·되돌리는 방법
미확인 검사와 다음 행동
```

실제 iPhone에서 볼 수 있는 **인증→원본 한 파일→첫 프레임→중간 탐색→닫기**를 일찍 완성한다. 전체 cache/변환/코퍼스 시스템을 만든 뒤 처음 연결하지 않는다.

### ARCH-05 — 제약 안에서 해결되지 않는 파일

정상 파일의 codec이 현재 브라우저와 승인된 실행 자원에서 처리되지 않는 경우:

- static reader의 결함과 codec 문제를 독립적으로 판별한다.
- client-side 점진적 demux/remux·가능한 제한 처리·기존 원본 decoder를 조사하고 실제 기기 성능으로 검증한다.
- 무료 인증 서비스가 긴 재인코딩을 감당한다고 가정하지 않는다. 큰 파일 전체를 wasm memory에 넣는 기본안을 채택하지 않는다.
- 확보하지 못한 기능은 정확한 유형·시도·실패 계층·필요 자원과 함께 `unsupported/unverified`로 남긴다. 이 목표를 `not-applicable`로 삭제하지 않는다.
- 그 분기의 한계가 확인돼도 UI·실제 파일 작업·정상 형식의 인증/재생 등 다른 승인된 작업을 계속한다.

현재 조건을 바꾸지 않고 달성할 수 없는 중요 요구가 구체적 반례로 남았을 때만, 추가 조건과 최소 비용의 결정을 보고한다. 초기 질문에 이미 답한 사용자를 A/B/C 투표로 다시 돌려보내지 않는다.

## 07. 품질·형식 지원 계약

### Q-01 — 품질 레벨 정의

| 레벨 | 정의 | 증거 | 사용자 기본 표시 |
|---|---|---|---|
| Q0 | 원본 파일 바이트 직접 전달·재생 | 동일 파일 버전의 선택 구간/필요 시 파일 해시와 전송 증거 | 상시 표시 없음, 상세 정보에서 `원본` |
| Q1 | 영상·음성 재인코딩 없이 컨테이너/전송 포장 변경 | codec mapping·변환 옵션·샘플 프레임/트랙 비교 | 상세 정보에서 `원본 스트림 · 재포장` |
| Q2 | 영상 스트림 유지, 비호환 음성 등 필요한 트랙만 변환 | 영상 copy 경로·음성 변환 프로파일과 출력 검사 | 상세 정보에 변환된 트랙 명시 |
| Q3 | 영상 재인코딩 필요 | 하위 단계 불가 원인·프로파일·원본 대비 품질/색 정보 | 상세 정보에 `호환 변환`; 중요한 품질 변경은 선택 전 짧게 알림 |
| EXT | Google/외부 플레이어 수동 열기 | 앱 밖 동작 또는 불투명 iframe | 앱 내부 재생 성공률에서 제외 |

Q1의 전체 파일 해시는 Q0와 달라도 된다. 컨테이너·타임스탬프 표기·bitstream 포장 변환이 있을 수 있으므로 `-c copy` 문자 존재만으로 모든 보존을 증명하지 않는다. FFmpeg는 streamcopy를 디코딩/인코딩 없는 패킷 전달로 설명하며, 출력 컨테이너에 필요한 정보·필터 등의 제약을 둔다. [R37]

### Q-02 — 기본 선택 규칙

```text
파일 접근 권한·정상 인증·실제 파일 버전 확인
→ 기기 능력과 실제 컨테이너/트랙 정보 확인
→ Q0가 가능하면 Q0
→ 컨테이너/포장만 문제면 Q1
→ 영상은 가능하고 음성만 문제면 Q2
→ 필요하면 로컬 네이티브 도구로 원인만 교차 검증（사용자 앱 설치 경로가 아님）
→ Q0/Q1/Q2와 승인된 브라우저/서비스 자원으로 불가능할 때만 실행 가능한 Q3 검토
```

이 순서는 **품질 선택**이다. 단순히 timeout 횟수가 늘 때마다 더 낮은 품질로 내려가는 오류 재시도 순서가 아니다.

### Q-03 — 품질 강등을 허용하지 않는 원인

인증 만료, 일시적 네트워크 오류, 429/요청 제한, 헤더 대기, 캐시 부족, 브라우저 제3자 쿠키, 파일 목록 실패를 Q3 또는 Google iframe 진입 근거로 사용하지 않는다. 먼저 원래 계층에서 복구·실패 설명을 한다.

저장 공간이 부족하면 구간 캐시 축소·불필요한 작업 정리·원본 streaming 경로를 검토한다. 캐시 한계를 곧바로 원본 코덱 실패로 부르지 않는다.

### Q-04 — 영상 정보 보존

해상도·프레임률·화면비·회전·색공간·range·bit depth·HDR metadata·음성 채널·트랙·자막을 각각 확인한다. 장치가 원본 색 표현을 못 하는 경우 tone mapping을 “원본 HDR 유지”라고 부르지 않는다.

Q3 기본값은 가독성과 재생 성공만을 위해 원본을 일괄 720p/1080p로 낮추는 것이 아니다. 검증된 codec/profile과 충분한 품질 설정을 사용하고, 불가피한 변화를 명시한다. 원본 비트레이트 숫자를 다른 codec에 그대로 넣는 것을 품질 동일성의 증거로 삼지 않는다.

### Q-05 — 사용자 선택과 기본값

기본 모드는 원본 품질 우선이다. 네트워크가 부족해도 저화질로 몰래 강등하지 않는다. 사용자가 원본 대기와 선택적 호환 변환 사이에서 결정할 수 있게 하되, 모든 파일을 열 때 기술 선택 대화상자를 반복하지 않는다. 중요 선호는 계정/기기 범위를 명시해 저장한다.

### Q-06 — 지원 완료의 단위

확장자 → 컨테이너·트랙 조합 → 기기/엔진 → 실제 파일 버전 순으로 지원 증거를 좁혀 기록한다. `.mp4` 하나의 통과는 모든 MP4의 통과가 아니다. MSE/HLS 라이브러리 지원은 기기의 영상·음성 디코딩 지원과 별개다. [R24][R28]

원본 파일이 정상이지만 이 앱에서 미지원이면 **미지원/미완료**로 기록한다. “파일 손상”으로 바꾸지 않는다.

## 08. 책임 분리·상태·인터페이스

### CORE-01 — 최소한의 모듈 경계

현재 큰 `app.js`를 한 번에 재작성하지 않는다. 실패 경로를 테스트로 고정한 뒤 책임별 함수를 이동/추출한다. 아래 이름은 설계 역할이지 필수 파일 이름이 아니다.

| 역할 | 소유 데이터/행동 | 소유하지 않는 것 |
|---|---|---|
| Session/Auth manager | 앱 세션, Google grant, 토큰 갱신, 계정 세대 | 파일의 재생 가능성 |
| Drive repository | 파일 ID metadata/read/write, 원격 결과 확인 | 플레이어 UI 상태 |
| Capability/probe | 컨테이너·트랙·장치 능력 | 성공하지 않은 형식 추정의 사실화 |
| Playback planner | Q0–Q3 계획, 이유, 선택 가능한 대안 | 실제 쓰기·인증 팝업 |
| Transport/source | range, 캐시, 무진행, 취소, 버전 고정 | 미디어를 보여줬다는 판정 |
| Playback adapter | 프레임·진행·오디오·seek·pause·종료 | Drive 파일 삭제 |
| Operation manager | 쓰기 요청 ID, 파일별 결과, 재확인, 복구 | 원격 실패를 로컬 성공으로 추정 |
| Presentation | 하단 제어·사용자 오류·접근성 | 토큰 자체·원본 쓰기 직접 실행 |

### CORE-02 — 상태 축을 분리한다

```text
AppSession: signed-out | authenticated | expired
GoogleGrant: disconnected | usable | renewing | reauth-required | denied
Source: idle | authorizing | probing | opening | streaming | retry-wait | failed | closed
Playback: idle | preparing | paused | playing | buffering | ended | error
Chrome: hidden | pointer-revealed | touch-revealed | keyboard-revealed
Mutation: prepared | submitted | verifying | confirmed | failed | uncertain | conflict | cancelled-before-submit
```

모든 축을 하나의 전역 상태 문자열로 합치지 않는다. 동시에 같은 사실을 여러 boolean으로 복제하지도 않는다. 예를 들어 `Playback=paused`가 `Chrome=visible`을 자동으로 의미해서는 안 된다.

### CORE-03 — 비동기 소유권

모든 비동기 결과는 최소한 다음 관련 소유권을 검사한다.

```text
accountKey / accountGeneration
credentialRevision
playbackId / mediaGeneration
fileId / fileVersion
operationId（쓰기）
```

- 오래된 계정·이전 파일·취소된 seek의 결과는 새 상태를 변경할 수 없다.
- credential revision과 token 문자열을 같은 것으로 보지 않는다.
- 같은 계정 토큰 갱신은 파일 목록·현재 영상·재생 위치를 초기화하지 않는다.
- 계정 전환은 새 계정에 이전 파일 ID·미확정 쓰기를 넘기지 않는다.
- 취소는 **로컬 작업 포기**와 **원격 쓰기 취소 성공**을 구분한다. 이미 보낸 PATCH는 abort 후에도 성공했을 수 있다.

### CORE-04 — 최소 인증 계층과 선택적 브로커의 API 예시

다음은 구현 계약 예시이며 현재 존재하는 API가 아니다. B-auth의 최소 session/OAuth부터 만들고 필요한 경로만 선택한다. `/media`, HLS, server operation API를 표에 있다는 이유로 모두 만들지 않는다. 사용자 입력 경로/URL을 그대로 전달하지 않고 담당 계층이 계정과 Drive 파일 ID를 검증한다.

| 메서드·경로 예시 | 역할 | 반환 원칙 |
|---|---|---|
| `GET /api/session` | 로그인·연결 상태 | 토큰·비밀 없이 계정 식별과 기능 권한 |
| `GET /oauth/start`·`GET /oauth/callback` | 승인된 OAuth 경로 | state 검증·origin 정리·서버 세션 |
| `POST /api/credentials/access`（직접 Drive 접근 시에만） | 짧은 token의 인증된 앱 전달 | session·Origin/CSRF 검사, 계정/revision, no-store, 메모리 수명. refresh token 제외 |
| `GET /api/files?parentId=...`（필요 시） | 파일 목록 | 실제 ID·버전·필요한 metadata·pagination |
| `POST /api/playbacks` | capability와 품질 선호로 계획 생성 | playbackId·Q 레벨·전송 경로·선택 이유 |
| `GET/HEAD /media/:playbackId/original` | 원본 range 응답 | 올바른 byte semantics, 인증된 사용자에게만 |
| `GET /media/:playbackId/hls/...` | 재포장/변환 manifest·segment | 계획과 동일한 파일 버전·트랙 |
| `DELETE /api/playbacks/:id` | 파생/전송 작업 닫기 | **Drive 파일 삭제가 아님**. 여러 번 닫아도 안전 |
| `POST /api/operations` | 휴지통·이동 의도 제출 | operationId·파일별 상태 |
| `GET /api/operations/:id` | 미확정 작업 조회 | confirmed/failed/uncertain/conflict 구분 |

HTTP `DELETE /api/playbacks/:id`와 Drive 영구 삭제는 전혀 다른 의미다. 사용자의 파일 삭제 API에는 `trash`라는 명시적 action을 사용해 혼동을 줄인다.

### CORE-05 — 공통 오류 계약 예시

```json
{
  "code": "UPSTREAM_STALLED",
  "category": "transport",
  "retryable": true,
  "userAction": "retry",
  "playbackId": "opaque-playback-id",
  "operationId": null,
  "retryAfterMs": null,
  "diagnosticId": "opaque-local-diagnostic-id"
}
```

허용 category 예시: `auth`, `permission`, `quota`, `transport`, `container`, `codec`, `storage`, `source-changed`, `mutation-conflict`, `unknown`.

응답과 로그에 upstream Authorization, refresh token, cookie, 개인 파일 전체 경로를 그대로 넣지 않는다. UI에 내부 stack trace나 장문 서버 응답을 출력하지 않는다.

### CORE-06 — 구독·작업 해제 계약

adapter는 `open`, `play`, `pause`, `seek`, `close`, `dispose`를 소유하며 `close/dispose`는 반복 호출해도 안전해야 한다. 이벤트 리스너·타이머·fetch·MSE buffer·native player·FFmpeg 작업이 이전 세션에서 살아남지 않도록 한다. 기능이 필요 없으면 추가 wrapper 대신 기존 추상화를 재사용한다.

## 09. 인증·세션·쿠키 상세 명세

### AUTH-01 — 서로 다른 네 가지 상태를 구별한다

| 상태 | 무엇을 뜻하는가 | 해서는 안 되는 결론 |
|---|---|---|
| 앱 로그인 세션 | 사용자가 Drive Original에 인증된 상태 | Google 웹사이트 쿠키도 쓸 수 있다는 뜻은 아님 |
| Google OAuth grant | 사용자 계정이 특정 앱·scope 접근을 승인 | 모든 파일을 읽고 수정할 수 있다는 뜻은 아님 |
| Google 액세스 토큰 | 제한된 수명의 API 호출 credential | 앱 세션의 수명과 같다는 뜻은 아님 |
| Google 웹 쿠키 | drive.google.com 등 웹 문서의 로그인 문맥 | API Bearer token으로 대체되어 iframe에 자동 전달되는 것이 아님 |

Google token model은 액세스 토큰 만료 시 사용자 동작에서 새 토큰을 받는 경로를 안내한다. `requestAccessToken({prompt:''})`를 타이머에서 부른다는 사실만으로 refresh token 방식의 무조작 갱신과 동등하다고 설명하지 않는다. [R01]

### AUTH-02 — 구조 A의 제한된 개선

정적 PWA를 유지하는 동안:

- 사용자 동작에서 재연결을 시작하고, 실패·팝업 취소를 구분한다.
- 토큰 갱신 중 기존 목록·재생 위치·좋아요·시청 기록을 보존한다.
- 미확인 계정 토큰을 SW에 먼저 전파하지 않는다.
- 네트워크 오류·특정 파일 403 때문에 전체 세션을 삭제하지 않는다.
- 백그라운드 복귀 시 `Date.now()`와 실제 토큰 만료를 확인하고, 이전 타이머가 정상 실행됐다고 가정하지 않는다.
- 자동 동작으로 갱신할 수 없는 경우 단일 재연결 진입점을 표시하며 팝업을 반복해서 띄우지 않는다.
- 만료된 credential을 localStorage에서 반복 재사용하거나 만료 시간을 늘려 정상으로 속이지 않는다.

이 단계는 실패 빈도와 상태 손실을 줄이는 것이다. 적합한 B-auth의 장기 credential 보관·정상 갱신과 동등한 증거로 취급하지 않는다.

### AUTH-03 — B-auth의 권장 흐름

웹용 authorization-code 경로와 적절한 offline access를 사용하고, 서버가 교환·검증·보관한다. 공식 인증 라이브러리를 우선 사용한다. [R02][R03]

```text
사용자 명시 로그인
→ 적합한 Google OAuth 요청
→ callback의 state/origin 등 검증
→ 서버가 code 교환
→ 서버가 계정 식별·실제 승인 scope 확인
→ 안전한 토큰 보관
→ 앱용 session cookie 발급
→ 브라우저는 앱 origin session/API 사용
→ 필요한 경우 짧은 access token을 받은 source/SW가 Drive 원본을 직접 읽음
→ 데이터 relay는 별도 채택된 경우에만 사용
→ 서버가 필요 시 Google access token 갱신
```

- client secret·refresh token은 공개 HTML/JS나 브라우저 저장소에 두지 않는다.
- refresh 응답에 새 refresh token이 없으면 기존 값을 유지한다. 빈 값으로 덮어쓰지 않는다.
- code 재사용·잘못된 state·계정 바꿔치기·외부 redirect를 거부한다.
- PKCE는 선택한 클라이언트 유형·SDK가 제공하는 정상 경로를 사용한다. 웹용 confidential client와 네이티브 공개 client를 혼용하지 않는다. 현재 제품 배포는 웹/PWA이며 네이티브 인증 앱을 추가하는 지시가 아니다. [R04]
- scope는 실제 승인값을 검사한다. 요청했다는 사실만으로 삭제·이동 버튼을 활성화하지 않는다.
- `drive.file`만으로 기존 전체 라이브러리가 자동 허용된다고 가정하지 않는다. 필요한 scope와 개인용 앱의 정책·예외 여부를 실제 설정에서 확인한다. [R05][R36]

### AUTH-04 — 갱신은 계정별 single-flight

권장 불변식:

```text
같은 accountKey의 refresh 요청은 동시에 최대 1개
같은 rejected credentialRevision의 자동 재시도는 유한
오래된 응답은 최신 credentialRevision을 지우지 못함
다른 계정으로 바뀐 요청은 재실행되지 않음
네트워크/권한 오류가 refresh token 삭제로 이어지지 않음
```

B-auth를 사용하면 refresh 조정은 그 계층이 소유한다. 여러 탭·두 기기의 독립 refresh loop가 경쟁하지 않게 한다. 서버리스의 인스턴스 메모리 mutex만으로 계정 전역 원자성을 보장한다고 주장하지 않는다. 실제 플랫폼이 제공하는 최소 직렬화·저장 수단과 revision 조건으로 해결하고 동시에 여러 요청을 보내 검증한다. 최종적 일관성 KV에 lock 값을 쓰는 것만으로 충분하다고 가정하지 않는다. 불필요한 분산 플랫폼이나 운영 서버를 새로 추가하지 않는다. [I04]

401 뒤 최신 revision이 이미 있으면 해당 credential로 한 번 재시도한다. 그래도 실패하면 이유를 분류한다. 같은 토큰 문자열이라도 revision이 다를 수 있다. 반대로 문자열만 다르다고 계정 식별 없이 신뢰하지 않는다.

### AUTH-05 — 오류별 처리

| 오류 | 자동 처리 | 사용자 상태/데이터 |
|---|---|---|
| 일시 네트워크 오류/5xx | 제한 재시도·backoff | 기존 계정/데이터 유지 |
| access token 만료 | 적절한 갱신 1회와 원래 요청 재개 | 같은 계정이면 현재 파일·위치 유지 |
| refresh `invalid_grant`/철회 | refresh loop 종료, 재연결 요구 | 원본·좋아요·작업 기록 삭제 금지 |
| 파일 `insufficientFilePermissions` | 해당 파일/작업 거부 | 전체 로그아웃 금지 |
| scope 부족 | 필요한 기능 제한·명시적 재승인 | 이미 가능한 읽기·재생 유지 |
| 403/429 rate limit | reason·Retry-After 기반 대기 | 로그인 팝업 금지 |
| 계정 식별 timeout | 결과 미확정, 기존 세션 보존 | 다른 계정이라고 추정하지 않음 |
| 다른 계정 선택 | 이전 세션 종료·요청 격리 후 새 계정 적용 | 이전 계정 state를 새 계정에 쓰지 않음 |

Google Drive는 HTTP 코드 안에서도 서로 다른 reason을 사용한다. 코드만으로 인증·quota·권한을 분류하지 않는다. [R07]

### AUTH-06 — 장기 세션의 운영 조건

Google 공식 문서는 refresh token의 철회·수명·발급 제한과 외부 Testing 프로젝트의 7일 조건을 설명한다. **현재 사용자 설정이 Testing인지 확인하지 않고 원인으로 확정하지 않는다.** [R05]

실제 Cloud 설정 읽기에서 확인할 항목:

```text
OAuth 프로젝트와 클라이언트 소유자
웹/네이티브 등 클라이언트 유형
redirect URI와 JS origin
실제 승인 scope
동의 화면 상태와 사용자 유형
테스트 사용자/조직 정책
최근 인증 실패 reason
운영 origin·세션 보관 정책
기존 appData 접근 가능성
```

앱 세션 유지 기간은 사용자 기대·보안·운영 범위에 맞춰 설정한다. 액세스 토큰 만료를 앱 로그아웃으로 보지 않되, 무한한 세션·영구 refresh token을 보장하지 않는다. 이 기기의 로그아웃과 Google 권한 전체 철회는 별도 동작으로 구분한다. 로컬 로그아웃 한 번이 다른 기기 grant까지 예기치 않게 철회하지 않게 한다.

### AUTH-07 — 같은 origin과 브라우저 세션

B-auth 채택 시 UI와 필요한 `/api`, OAuth callback을 같은 HTTPS origin으로 구성하는 것을 우선한다. `/media`는 별도로 채택한 relay/파생 전달 경로가 있을 때만 같은 origin에 둔다. 브라우저에는 앱 세션을 담은 `Secure`·`HttpOnly` cookie를 사용하고, 적합한 `SameSite`·Path·Domain 정책을 적용한다. `__Host-` prefix 사용 시 해당 조건을 맞춘다.

OAuth redirect·팝업 복귀·PWA 복귀에서 쿠키가 전달되는지 실제 테스트한다. `SameSite` 값을 무조건 가장 강하게 설정했다는 이유로 인증 redirect를 깨뜨리거나, 반대로 문제를 피하려고 모든 cross-site 요청을 허용하지 않는다.

브라우저 `<video>`와 Safari native HLS는 일반 JS fetch와 요청 구성 방식이 다를 수 있다. **커스텀 Authorization 헤더를 모든 segment 요청에 마음대로 붙일 수 있다고 가정하지 않는다.** 현행 직접 경로에서는 SW/source adapter가 앱 세션으로 받은 짧은 token을 사용해 인증된 fetch를 수행하고 미디어 요소에는 적합한 stream을 전달하는 계약을 검증한다. relay가 채택됐을 때는 앱 session cookie의 동일 origin 경로를 검증하고, 필요한 경우 제한된 미디어 capability를 설계한다. Google token을 media URL에 넣는 우회는 하지 않는다.

### AUTH-08 — 쿠키 문제의 올바른 해결 범위

WebKit은 제3자 쿠키 제한과 Storage Access API를 문서화한다. 부모 앱이 Google iframe 문서의 로그인·쿠키·DOM을 임의로 고칠 수 있다고 가정하지 않는다. [R14]

- 정상 재생은 Google iframe을 필수로 사용하지 않는다.
- Google 쿠키 복사·브라우저 프로필 추출·보안 기능 일괄 해제는 하지 않는다.
- `allow="autoplay"`, CORS 플러그인, iframe CSS 변경을 쿠키 인증 해결책으로 보고하지 않는다.
- 호환 iframe을 사용자가 수동으로 열었다면 앱 소유 액션 패널은 닫거나 숨길 수 있어야 한다. iframe의 `load`는 문서 로드만 증명한다.
- 로그인 재현을 위해 사용자 Google 세션 전체를 로그아웃시키거나 쿠키를 일괄 삭제하지 않는다. 새 테스트 프로필을 우선 사용한다.


### AUTH-09 — 직접 데이터 경로의 credential 전달과 PWA 복귀

- 짧은 access token을 전달하는 endpoint는 현재 앱 세션에만 응답하고 `no-store`를 적용한다. Origin·CSRF·계정 revision을 검사하며 제3자 페이지가 읽지 못하게 한다.
- token을 정적 설정·쿼리스트링·HTML·localStorage 장기 저장·오류·HAR·디버그 로그에 남기지 않는다. 기존 저장 모델 전환에는 데이터 이관 순서를 적용한다.
- SW 재시작 시 암묵적인 전역 마지막 token을 재사용하지 말고 요청 client·계정/credential 세대에 맞춰 다시 얻는다. 새 인증 구조와 옛 GIS refresh를 병렬로 실행하지 않는다.
- 같은 HTTPS origin은 설계 단순화이며, iPhone 탭·홈 화면 PWA가 모든 저장소를 자동 공유한다는 보장이 아니다. 각 실행 환경에서 로그인 진입·callback·앱 복귀·세션 지속을 실제로 검사한다.
- 새 OAuth client와 새 Google Cloud 프로젝트는 다른 변경이다. 기존 프로젝트·앱 정체성을 우선 재사용하고, 기존 appData 가시성은 동일 계정이라는 이유로 추정하지 않는다.
- 무료 계층의 cold start·재시작·요청 동시 실행·저장소 일시 장애가 계정 삭제나 갱신 폭주로 이어지지 않게 한다.

## 10. 구간 전송·장시간 재생·캐시

### TR-01 — 최초 재생의 critical path

```text
사용자 열기
→ 필요한 credential 확보
→ 이미 있는 metadata 검증 / 부족한 정보만 조회
→ 최소 probe 또는 확인된 capability 재사용
→ 원본/파생 source 열기
→ 첫 데이터
→ 첫 프레임 + 실제 재생 진행
```

전체 Drive scan·좋아요 상태 전체 병합·모든 파일 probe·전체 원본 다운로드·썸네일 일괄 생성은 첫 프레임의 선행 조건이 아니다. 현재 파일에 필요한 일만 먼저 한다.

지원 확인된 원본은 구간 전송을 우선한다. 캐시가 재생을 돕게 하되, “OPFS가 있으니 먼저 전체 저장”을 기본 규칙으로 고정하지 않는다. 공식 Drive API는 blob 파일의 `Range` 부분 다운로드를 제공한다. [R06]

### TR-02 — 원본 reader 계약

reader 입력은 검증된 `accountKey + fileId + fileVersion + range`다. 사용자가 넘긴 임의 URL이나 `G:` 전체 경로를 원격 공개 endpoint에서 받아 열지 않는다.

메타데이터·바이트 응답은 동일한 파일 버전에 속해야 한다. 관련 필드가 없는 경우 이 사실을 명시하고 최신 metadata 재조회·캐시 무효화 전략을 사용한다. Drive file version/checksum이 모든 형식에 동일하게 존재한다고 가정하지 않는다. [R08]

### TR-03 — HTTP byte semantics

HTTP 범위·조건부 요청의 기본 근거는 RFC 9110이다. 아래는 앱이 지원할 계약이다. [R15]

| 경우 | 요구 |
|---|---|
| `GET` without Range | 정상 전체 표현 응답을 streaming으로 제공. 메모리에 전부 적재하지 않음 |
| `HEAD` | 본문 없음. 실제 size/type/지원 능력 기반 응답. Drive upstream이 같은 HEAD를 지원한다고 가정하지 말고 metadata 경로 사용 가능 |
| `bytes=0-1` | Safari식 작은 첫 요청을 정확히 처리 |
| `bytes=start-end` | 범위·파일 크기·본문 길이 일치 |
| `bytes=start-` | 열린 범위 처리; 큰 응답이어도 streaming 유지 |
| `bytes=-suffix` | 파일 끝 구간을 읽을 수 있음 |
| 마지막 바이트 경계 | off-by-one 없이 올바른 206/416 |
| 범위를 벗어남 | 적절한 unsatisfied range 응답, 허위 데이터 금지 |
| malformed/multiple Range | 실제 지원 범위와 표준에 맞게 처리. 모든 미지원 문법을 동일 416로 뭉개지 않음 |
| Range를 무시한 upstream 200 | 가짜 206·가짜 Content-Range 금지. 같은 수신 stream을 필요 이상 중복 다운로드하지 않음 |
| 부분 206 | 요청한 길이와 다르다는 이유만으로 무조건 거부하지 않고 실제 Content-Range·본문과 의미 검증 |
| 조건부/If-Range | 사용하는 validator가 실제 지원·검증 가능한지 확인. 로컬 추정 ETag를 upstream 원자성 보장으로 착각하지 않음 |
| 2 GiB·4 GiB 이상 offset | 32비트 bitwise 계산/overflow 금지, 안전한 정수·문자열 처리 |

파일 크기·offset·기간을 검증하고 `NaN`, 음수, 무한값, overflow를 거부한다. metadata size를 숫자로 사용할 때 안전 정수 범위를 확인한다.

### TR-04 — upstream 헤더와 콘텐츠 검증

- 실제 콘텐츠와 MIME이 어긋나는지 검사한다. 확장자나 쿼리의 MIME 하나로 잘못된 응답을 강제로 영상으로 위장하지 않는다.
- 오류 HTML·JSON을 `video/mp4`로 라벨링하지 않는다.
- 압축/자동 decompression 때문에 Content-Length·Content-Encoding이 어긋나지 않게 한다.
- upstream 인증·쿠키·hop-by-hop 헤더를 무조건 downstream으로 복사하지 않는다.
- 원본 byte range는 전송 중 변형하지 않는다. `no-transform` 정책과 실제 경로를 맞춘다.
- redirect가 필요하면 신뢰 가능한 API 경로로 제한하고 credential이 임의 origin으로 유출되지 않게 한다.
- 헤더 전달과 첫 바이트 사이의 지연도 계측한다. `fetch()`가 resolve됐다고 첫 프레임 준비가 끝난 것은 아니다.

### TR-05 — MP4/MOV의 앞·뒤 인덱스 접근

FFmpeg 문서는 MOV/MP4 metadata가 한 위치, 흔히 파일 끝에 있을 수 있음을 설명한다. `faststart`는 인덱스 이동의 별도 pass이고 fragmentation과 같은 기능이 아니다. [R30]

실패 파일에서 `moov`/index 위치, tail request, source seek 가능성을 확인한다. reader가 앞부분만 읽어 전체를 기다리거나, 끝 구간 요청을 잘못 처리하는지 검사한다.

해결 경로는 정상 tail range, 제한된 인덱스 조회, 필요한 파생 재포장이다. **원본에 faststart를 직접 적용하거나 원본 파일을 덮어쓰지 않는다.** 파생 MP4를 끝까지 완성해야만 쓸 수 있는 설계를 긴 영상의 즉시 재생 해법으로 잘못 채택하지 않는다.

### TR-06 — 무진행 감시와 복구

각 대기는 서로 다른 clock을 사용한다.

```text
credential wait
headers wait
first-byte wait
body no-progress
decoder/frame no-progress
seek completion wait
```

초기 목표값은 17장에서 제시한다. 고정 타이머가 사용자의 긴 정상 재생 전체를 끊어서는 안 된다. 전경/백그라운드·사용자 pause·네트워크 offline·브라우저의 버퍼링 상태를 구분한다.

body stream이 이미 전송된 뒤 실패하면 새 HTTP JSON 응답을 덧붙일 수 없다. 연결을 적절히 종료하고 클라이언트의 source 복구 계약으로 넘긴다. 부분 데이터를 조용히 이어 붙여 손상된 파일처럼 만들지 않는다.

복구 예산은 adapter와 broker와 SW가 중복 소유하지 않는다. 사용자 의도 하나에 전체 재시도 예산 하나를 적용하고, 401 자동 갱신·일시 전송 재시도·사용자 명시 재시도를 구분한다.

### TR-07 — 장시간 재생 중 만료·절전·변경

- 처음 재생에 성공해도 수십 분 뒤 새 Range/segment 요청 때 재인증이 필요할 수 있다.
- 짧은 미디어 URL 만료가 장시간 seek·재연결을 깨뜨리지 않게 한다. Google token을 URL에 넣지 않는다.
- 권한이 철회되면 무한히 새 요청을 시도하지 않는다. 이미 받은 버퍼와 향후 접근 제어를 구분해 종료·재연결 UX를 명확히 한다.
- source가 중간에 바뀌면 이전 cache와 새 byte를 섞지 않는다. 재생을 안전하게 재시작하거나 변경 사실을 짧게 알려 사용자가 선택하게 한다.
- 일시정지·백그라운드 동안 진행이 없다고 코덱 실패로 전환하지 않는다.

### TR-08 — backpressure·취소

브라우저가 느리게 읽으면 upstream과 변환 생산 속도도 제어한다. 서버/프로세스가 영상을 끝까지 미리 소비해서 메모리·디스크를 채우지 않는다.

재생 닫기·다른 파일·다른 seek를 수행하면 불필요한 fetch/segment/FFmpeg 작업을 취소한다. 공유 중인 파생 결과는 consumer lease를 확인하고 마지막 consumer가 떠난 뒤 정리한다. `kill all ffmpeg`, 이름으로 프로세스를 일괄 종료하는 방식은 금지한다.

### TR-09 — 캐시의 범위

기본 key:

```text
account namespace
+ fileId
+ content version/fingerprint
+ byte range 또는 representation profile
+ track selection
+ packaging/decoder configuration version
```

동일 파일명이나 같은 `G:` 상대 경로만으로 공유하지 않는다. 캐시 hit도 접근 권한 검사를 우회하지 않는다.

- 메모리·디스크 상한을 별도 둔다.
- cache eviction은 활성 재생/작업의 lease를 존중한다.
- 부분 파일은 완료 파일과 구분하고 원자적으로 확정한다.
- source 변경·trash·계정 철회 시 파생 사용을 무효화한다.
- 서비스 재시작 시 임시 파일·orphan 작업을 bounded cleanup한다.
- 캐시가 없어도 원본 직접 경로가 가능한 파일은 재생할 수 있어야 한다.

rclone의 VFS 옵션을 채택할 때는 작은 구간의 요청 수와 큰 구간의 낭비 대역폭을 비교한다. 공식 예시의 버퍼·병렬 값을 자신의 측정 없이 복사하지 않는다. [R20]

### TR-10 — 우선순위

```text
현재 재생·현재 seek
> 사용자 명시 파일 작업과 필요한 인증
> 가까운 다음 파일 최소 예열
> 화면 내 썸네일
> 상태 동기화·metadata 후속 페이지
> 전체 코퍼스 분석·캐시 정리
```

실제 쓰기의 correctness를 백그라운드 최적화보다 우선하되, 일괄 파일 작업이 재생을 독점적으로 방해하지 않게 별도 제한을 둔다. 위 순서는 제안이며 사용자 사용 방식과 trace에 따라 세부 예산을 조정한다.


### TR-11 — 계측을 위해 원본 전송을 악화시키지 않는다

타임라인을 얻기 위해 전체 stream을 복제·소비하거나, 모든 response body를 Blob/ArrayBuffer로 바꾸거나, 진단용 duplicate download를 정상 경로에 추가하지 않는다. stream 관측은 backpressure·abort·범위 의미를 보존하고 실제 누적 바이트/첫 바이트만 제한적으로 기록한다.

직접 경로와 relay 경로를 비교할 때 계측 비용을 분리한다. 헤더/본문 취소·실제 재생이 증거라면 동일 영상의 전체 해시를 매 재생마다 계산하는 것은 필요하지 않다. 미디어 fingerprint와 선택 구간의 검증 근거를 합리적으로 선택한다.

<a id="media-processing"></a>
## 11. 재포장·부분 변환·전체 변환

### MEDIA-01 — probe 결과와 capability로 계획한다

`canPlayType`, MediaSource/ManagedMediaSource 유무, 필요한 경우 MediaCapabilities 결과, 실제 sample 재생을 결합한다. 사용자 agent 문자열만으로 HEVC/HDR 등을 확정하지 않는다. 같은 브라우저 이름이어도 기기와 빌드에 따라 다를 수 있다. [R24][R28]

판정 cache는 기기/엔진 버전과 source 조합에 범위를 둔다. 한 파일의 오류가 같은 확장자 전체의 영구 미지원으로 확산되지 않게 한다.

### MEDIA-02 — 재포장 규칙

영상과 음성이 모두 지원되고 컨테이너만 문제면 Q1을 시도한다. 스트림 선택을 명시하고, 빠진 audio/subtitle/rotation/color metadata가 없는지 확인한다.

FFmpeg의 기본 stream selection이나 자동 encoding에 맡겨 의도치 않게 영상이 재인코딩되지 않게 한다. 실제 실행 인자와 선택 codec을 private diagnostic에 남기되 token 포함 URL·개인 경로는 정제한다. [R37]

### MEDIA-03 — HLS를 선택하는 경우

HLS는 모든 형식 문제를 해결하는 주문이 아니라 출력 전달 규격이다. 해당 codec을 처리할 수 있는 client와 올바른 manifest/segment가 함께 필요하다. Safari native HLS와 hls.js는 feature detection과 실기기 비교로 선택한다. 한 영상에 두 엔진을 동시에 attach하지 않는다. [R28][R39]

필수 검증:

- 전체 재생 길이, media timeline, segment duration, timestamp discontinuity를 올바르게 표현한다.
- 실제로 아직 만들지 못한 segment를 영구 404로 내보내지 않는다. 예약·bounded 준비 대기·실패 계약을 둔다.
- 안정된 VOD timeline 없이 앞부분만 늘어나는 playlist로 90% seek를 지원했다고 주장하지 않는다.
- segment는 재생 가능한 경계에서 시작해야 한다. streamcopy의 keyframe 제약을 무시하고 정확히 같은 길이 조각을 강제로 주장하지 않는다.
- 서로 다른 generation/track/profile의 segment를 한 재생에 섞지 않는다.
- 보호된 manifest·segment 요청의 인증이 Safari/PWA에서도 동작하는지 확인한다.
- ABR 기본값으로 사용자가 원하지 않은 품질 강등을 일으키지 않는다. Q0/Q1/Q2/최고품질 정책과 player 설정을 맞춘다.

### MEDIA-04 — 긴 영상의 임의 탐색

단순히 `ffmpeg`를 0초에서 시작하고 90% 위치가 생성될 때까지 기다리는 것은 합격이 아니다.

권장 계약:

```text
사용자 targetTime
→ 현재 seekGeneration 갱신
→ source index/keyframe에서 안전한 시작점 찾기
→ 해당 구간 파생 작업 또는 검증된 기존 결과 재사용
→ 출력 timestamp와 player timeline 연결
→ 목표 부근 프레임 표시
→ 이전 seekGeneration 결과 무시/정리
```

원본 streamcopy에서 정확한 프레임 seek가 보장되지 않는 경우 탐색 근사 범위와 seek 후 실제 위치를 기록한다. 무재인코딩을 유지한다며 클릭한 시각과 수십 초 다른 화면을 조용히 보여주지 않는다. 큰 GOP·VFR·음성 시작 offset을 검사한다.

입력 probe·index가 부족하면 분석을 단계적으로 확장한다. 이유 없이 모든 파일의 전체 인덱스를 미리 생성하지 않는다.

### MEDIA-05 — 음성만 비호환이면 Q2

영상은 copy하고 필요한 음성 트랙만 지원 codec으로 변환한다. 원본 무음 영상은 오류가 아니고, 사용자 선택 트랙이 있는 파일은 임의의 다른 언어 트랙으로 바꾸지 않는다. 채널 혼합·샘플률 변경이 필요하면 기록한다.

자막은 가능한 client rendering/sidecar 경로를 먼저 검토한다. 자막을 영상에 태우는 것은 영상 재인코딩을 요구할 수 있으므로 Q1이라고 부르지 않는다.

### MEDIA-06 — Q3는 증거 기반 최후 경로

먼저 원본 디코딩 실패가 transport/auth와 독립인지 확인한다. 하드웨어와 소프트웨어 변환 후보를 비교하되, 특정 하드웨어 encoder가 설치돼 있다고 가정하지 않는다.

- 선택한 기기의 지원 codec/profile/bit depth에 맞춘다.
- 사용자 원본을 덮어쓰지 않고 제한된 파생 결과만 생성한다.
- 원본 해상도·프레임률을 불필요하게 변경하지 않는다.
- decoder가 처리하지 못한 것을 encoder 품질 상향만으로 해결하려 하지 않는다.
- 장시간 변환에서 실시간 처리율·열·CPU/GPU·메모리·디스크를 측정한다.
- 실제 원본보다 처리율이 부족하면 반복 재생 실패가 아니라 가용한 품질/기기/대기 선택을 명확히 제공한다.

### MEDIA-07 — 이미지·애니메이션

이미지를 원본 표시할 수 있으면 그 경로를 유지한다. GIF와 animated WebP는 목록에서만 정지하고 재생 화면에서는 frame delay·loop·alpha가 보존돼야 한다. 이미지의 표시 실패를 Google 영상 iframe으로 넘기지 않는다.

큰 이미지의 디코딩 자원과 표시 크기를 분리한다. 썸네일을 원본 표시로 라벨링하지 않는다. 지원되지 않는 이미지 변형에 변환이 필요하면 별도 derivative와 원본의 관계를 명시하고 원본을 보존한다.

### MEDIA-08 — 네이티브 비교는 진단이며 제품 배포가 아니다

VLC/libVLC·FFmpeg/ffprobe 등은 동일 원본의 전송/컨테이너/디코더 문제를 나누는 로컬 비교 도구로 사용할 수 있다. VLC 앱 전체·VLCKit·FFmpeg 빌드의 라이선스와 역할은 다르다. [R17][R18]

네이티브 설치·서명·앱스토어·WebView wrapper를 사용자 정상 사용 경로에 추가하지 않는다. 로컬 native 재생 성공은 원본 파일이 브라우저 경로에서 실제 재생됐다는 증거가 아니다. 비교 결과를 client-side 재포장/제한 처리 또는 구현 한계 판정에 사용한다.

### MEDIA-09 — 무료 서버리스와 브라우저 처리의 경계

B-auth에는 native FFmpeg 프로세스·무제한 CPU·대용량 영속 디스크가 있다고 가정하지 않는다. 컨테이너 분석과 Q1은 필요한 입력 구간만 읽고 seek 가능한 점진 처리로 검증한다. audio/Q3 처리를 브라우저에서 선택하면 실제 기기 메모리·열·처리율·탐색·취소를 측정한다. ffmpeg.wasm 전체 파일 처리로 4 GiB 파일 문제를 덮지 않는다.

운영 제약 안에서 지원 경로를 아직 확보하지 못했으면 정확한 file/codec/device 조합과 시도한 경로를 남긴다. 단순 정적 앱이라서 불가하다고 미리 포기하지도, 무료 함수로 모든 변환이 가능하다고 약속하지도 않는다.

<a id="corpus"></a>
## 12. 형식 조사·코퍼스 검증

### CORPUS-01 — 조회를 세 단계로 분리한다

1. **Metadata inventory:** 경로/ID·확장자·MIME·size·modified/version·권한을 수집한다.
2. **Bounded probe:** 필요한 파일 header/tail/index와 미디어 stream 정보를 읽는다.
3. **Decode/playback:** 실제 sample·위치·장시간 재생과 영상/음성을 확인한다.

이 셋은 비용과 증거 수준이 다르다. 파일 내용을 읽지 않은 inventory를 “모든 파일 검사 완료”라고 부르지 않는다. `G:` 스트리밍 placeholder를 열면 다운로드·캐시 생성이 발생할 수 있으므로, 읽기라도 자원 비용을 고려한다.

### CORPUS-02 — 파일 식별

Drive file ID를 기준으로 파일명·경로·크기·버전을 대응시킨다. 중복 이름·바로가기·같은 파일의 다른 표시 위치를 처리한다. 자료가 불일치하면 소유 시스템을 확인한다. `G:`의 동기화 지연 때문에 이름만으로 API 파일을 수정하지 않는다.

실제 대상 media root ID는 확인 후 저장한다. 폴더명 `ㅇㅎㅎ`만으로 계정 전체에서 첫 검색 결과를 사용하지 않는다.

### CORPUS-03 — probe 항목

```text
container / format names / duration / size / bitrate
video codec / tag / profile / level / pixel format / bit depth
width / height / sample aspect ratio / display aspect ratio
average & real frame rate / rotation / color fields / HDR side data
audio codec / sample rate / channel layout / language / default disposition
subtitle codec / track / language / disposition
index presence / known moov or cue location / seek behavior
probe version / byte budget / elapsed / result confidence
```

ffprobe는 선택한 `show_entries`, streams/format/side data 등으로 분석 정보를 얻을 수 있다. `-show_packets`·`-show_frames`를 수천 파일 전체에 무제한 적용하지 않는다. 필요한 구간과 출력량을 제한한다. [R38]

초기 실행 인자는 예시를 그대로 복사하기보다 설치된 ffprobe 버전과 실제 파일에 맞춰 검사한다. metadata가 빠졌다고 즉시 손상으로 분류하지 않는다. 4 GiB 파일 전체를 일괄 hydration해 코덱 이름 하나 얻는 방식은 피한다.

### CORPUS-04 — 위험도 기반 우선순위

먼저 사용자 실패 파일, MKV 8개·AVI 5개·BMP 1개, 가장 큰 MP4/MOV, 긴 영상, 회전 영상, 음성이 안 나오는 영상, animated WebP/GIF를 검사한다. 그다음 발견된 codec/profile/bit-depth/HDR/track 조합별 대표를 확장한다.

rare extension만 검사하고 흔한 MP4를 모두 동일시하지 않는다. 각 조합에서 작은 파일·큰 파일·긴 파일·네트워크 조건을 조합한다.

### CORPUS-05 — 지원 행렬의 열

| 필드 | 의미 |
|---|---|
| corpusVersion | 어느 시점의 파일 집합인가 |
| fileKey / fileVersion | 어떤 실제 파일 버전인가 |
| extension / container / streams | 실제 형식 |
| device / OS / engine / app SHA | 재생 환경 |
| Q path | 실제 사용한 품질 경로 |
| metadataProbe / firstFrame / audio / seek / sustained | 증거를 항목별 구분 |
| result | passed / unsupported / permission-blocked / corrupt-confirmed / unverified |
| evidence | trace·검증 로그·필요 시 비공개 screenshot 위치 |

### CORPUS-06 — 전수와 표본의 구분

- 파일 inventory는 대상 범위를 모두 열거한다.
- 가능한 범위에서 영상 전체의 bounded metadata/probe와 이미지 header 분류를 수행하고, 예산 때문에 못 한 항목을 남긴다.
- 희귀/실패/코덱 조합 대표는 실제 기기에서 first frame·audio·seek·지속 재생을 확인한다.
- 모든 파일이 실제 재생된 것이 아니라면 “8,469개 모두 재생 검증”이라고 쓰지 않는다.
- 사용자가 특정 파일의 동작을 요구하면 그 파일은 개별 인수 대상이다. 같은 codec 대표 통과로 대체하지 않는다.

지원 행렬의 미확인 항목을 분모에서 빼 통과율을 높이지 않는다. 기능 지원 완료와 코퍼스 전수 실재생 확인은 별도 지표로 보고한다.

### CORPUS-07 — 손상 판정

권한·네트워크·파일 버전 불일치를 먼저 제외한다. 필요한 원본 구간을 정확히 받은 독립 도구에서도 구조/디코딩 실패가 확인된 경우에만 `corrupt-confirmed` 후보로 분류한다. 부분 검사로 전체 파일 무손상을 보장하지 않는다.

실험 결과가 엇갈리면 `unverified` 또는 앱/엔진 미지원으로 남기고 다음 판별 실험을 기록한다. 사용자가 제출한 민감 미디어를 공개 이슈·외부 디코딩 사이트로 업로드하지 않는다.

<a id="mutations"></a>
## 13. 파일 삭제·이동·결과 확인

### MUT-01 — Drive 서버 상태가 성공의 기준

파일 작업은 **올바른 계정의 동일한 Drive file ID**에 대해 수행하고, 원격 metadata로 확인한다. 로컬 카드 제거·클릭 애니메이션·빈 성공 응답·`G:` 파일 탐색기 표시만으로 확정하지 않는다.

공식 API의 휴지통과 영구 삭제는 다르며 `canTrash`, `canDelete`, `canUntrash`도 별도 capability다. 일반 삭제는 휴지통 이동으로 구현한다. [R10]

### MUT-02 — 명시적인 작업 의도

작업 하나의 입력 예시:

```json
{
  "operationId": "client-generated-unique-id",
  "action": "move",
  "accountKey": "server-validated-account-reference",
  "items": [
    {
      "fileId": "verified-file-id",
      "expectedParents": ["verified-old-parent-id"],
      "expectedVersion": "observed-version",
      "targetParentId": "verified-target-folder-id"
    }
  ]
}
```

operation 소유 계층은 accountKey를 요청값만으로 신뢰하지 않고 실제 인증 세션과 대조한다. 서버 API를 선택했다면 서버에서 강제한다. file name/path가 아니라 ID를 사용한다. 동일 operationId에 다른 payload가 오면 충돌로 거부한다.

`trash`, `move`는 별도 action이다. 일반 휴지통 UX가 Drive의 영구 DELETE로 매핑되지 않게 한다. 원본 media 삭제를 playback session DELETE와 혼동하지 않는다.

### MUT-03 — 요청 전 확인

파일과 목적지의 현재 metadata를 필요한 만큼 조회한다.

```text
id / parents / trashed / driveId / mimeType / shortcutDetails
version（사용할 수 있는 경우）
capabilities.canTrash / canUntrash / canDelete
capabilities.canMoveItemWithinDrive / canMoveItemOutOfDrive
목적지 capabilities.canAddChildren
필요한 resourceKey
```

현재 scope·권한·소유 계정·대상 파일인지 확인한다. shortcut을 이동/삭제하는지 실제 target을 이동/삭제하는지 명확히 구분한다. 원본 fileId로 조용히 따라가 target을 지우지 않는다.

Drive 이동은 현재 부모와 목적지를 확인한 `files.update`의 `addParents/removeParents`로 수행한다. 파일이 이미 목적지에 있으면 remote no-op 성공으로 분류할 수 있으나, 처음부터 상태를 추정하지 않는다. [R09][R11]

### MUT-04 — 영속적인 파일별 상태

```text
prepared
  ├─ cancelled-before-submit
  └─ submitted
        └─ verifying
              ├─ confirmed
              ├─ failed
              ├─ uncertain
              └─ conflict
```

각 상태 의미:

| 상태 | 의미 |
|---|---|
| prepared | 사용자 의도와 pre-state를 보관했으나 아직 전송 전 |
| submitted | 원격 요청이 전송됐을 가능성이 있음 |
| verifying | 결과를 독립 GET으로 확인 중 |
| confirmed | 현재 확인된 원격 상태가 요청한 postcondition과 일치 |
| failed | 명시적인 거부/실패와 원격 미반영을 확인 |
| uncertain | 요청이 적용됐을 수 있으나 확인 불가 |
| conflict | 외부 변경/다른 사용자 작업 등으로 기대 상태와 어긋남 |
| cancelled-before-submit | 원격 전송 전에만 취소됨 |

브라우저에서 Drive 쓰기를 수행하는 구성은 refresh/reload에도 제출한 미확정 작업을 복구할 최소 영속 기록을 갖춘다. 서버 operation API를 채택했다면 그 계층이 ledger를 소유한다. B-auth만 추가한 것은 모든 쓰기 소유권을 서버로 옮겼다는 뜻이 아니다. 어느 구성이든 mutation·readback·recovery의 소유자를 하나로 두고, 전역 “진행 중” boolean만으로 부분 성공을 잃지 않는다.

### MUT-05 — 원격 postcondition

| 작업 | 요청 | 확인할 결과 |
|---|---|---|
| 휴지통 이동 | `PATCH {trashed:true}` | 동일 ID의 `trashed:true` 또는 적절한 권한 범위 내 명확한 결과 |
| 이동 | 현재 부모 제거 + 대상 부모 추가 | 동일 ID의 `parents`가 실제 목적지와 일치 |
| 테스트 복구 | 승인된 이전 상태로 복구 | 이전 부모/휴지통 상태 일치 |

`404`만 보고 삭제 성공이라 단정하지 않는다. 접근 권한 상실·다른 계정·영구 삭제 등 구별 불가한 경우가 있다. 응답 JSON parse 실패를 `{}`로 바꿔 확정 성공 처리하지 않는다.

이동 응답에 `parents`가 없으면 GET으로 확인한다. `[target]`을 채워 사실처럼 저장하지 않는다. metadata query는 필요한 `fields`를 명시하되 검증할 필드를 누락하지 않는다.

### MUT-06 — 네트워크 단절 뒤의 모호성

PATCH 전송 직후 응답이 끊겼을 때:

1. 실패 toast 확정이나 무조건 재전송을 하지 않는다.
2. 동일 계정·동일 ID로 최신 상태를 읽는다.
3. postcondition과 일치하면 confirmed로 정리한다.
4. 기존 상태와 일치하고 재시도 가능성이 분명하면 제한된 재시도를 고려한다.
5. 다른 상태이거나 읽을 수 없으면 uncertain/conflict로 남긴다.

이것은 완벽한 exactly-once 원격 API를 만든다는 뜻이 아니다. 외부 시스템에 대한 원자성이 없는 부분은 과장하지 않는다. 앱의 idempotency key·로컬 직렬화·원격 pre/post 확인을 결합해 중복과 오판을 줄인다.

ETag/If-Match 같은 조건부 쓰기를 활용할 때는 해당 API의 지원과 실제 실패 동작을 확인한다. preflight GET만 했다고 외부 앱과의 경쟁까지 원자적으로 막혔다고 주장하지 않는다.

### MUT-07 — 일괄 작업과 계정 변경

일괄 작업은 파일별 ledger가 필요하다. 두 파일 성공 후 세 번째에서 만료·오류·계정 전환이 발생해도 앞선 성공 사실을 보존한다.

- 작업의 origin accountKey는 불변이다.
- 계정 전환 후 이전 operation을 새 계정으로 재실행하지 않는다.
- 아직 전송 안 된 항목은 취소할 수 있지만 이미 submitted인 항목은 확인 대상이다.
- 전체 `owner.assert()`가 실패했다고 개별 원격 성공 이력을 지우지 않는다.
- 미확정 기록이 다른 계정 UI에 표시되거나 새 계정 데이터에 합쳐지지 않게 한다.
- 다른 앱에서 같은 파일을 다시 이동하면 자동으로 되돌리지 않는다. 최신 원격 상태와 충돌로 표시한다.

### MUT-08 — UI 반영과 복구

확인된 성공 항목만 확정 제거/이동한다. 낙관적 UI를 사용할 경우 pending 표시·원래 위치 복구·재확인 상태를 설계한다. 실패한 항목까지 전체 목록에서 지우지 않는다.

사용자 결과 문구는 `3개 이동됨`, `2개 실패`, `1개 확인 중`처럼 행동 중심으로 짧게 한다. 내부 API와 로컬 캐시 설명은 진단으로 보낸다. 성공 개수와 실패/미확정 분모가 합쳐 원래 대상 수와 일치해야 한다.

좋아요는 fileId에 연결되므로 폴더 이동만으로 취소하지 않는다. 휴지통 항목의 표시·복구 후 좋아요/시청 상태도 기존 규칙을 명확히 유지한다.

### MUT-09 — 클라우드와 G: 검증 분리

같은 파일 ID 기준으로 다음을 비교한다.

```text
앱 operation 결과
→ 공식 Drive API 최신 GET
→ 독립적인 Drive 웹 화면
→ Drive for desktop의 G: 동기화 반영
```

클라우드에서 성공했지만 `G:`가 늦으면 데스크톱 동기화의 별도 상태다. 반대로 `G:`만 움직이고 API 상태가 다른 경우 해당 조작 경로를 조사한다. 로컬 파일을 수정해 API 구현 결함을 가리지 않는다.

### MUT-10 — 실쓰기 테스트 안전 범위

01.2에서 이번 작업이 생성한 일회용 테스트 데이터의 실쓰기를 허용한다. 실제 로그인·scope·접근을 확인하고 고유 run ID를 포함한 전용 폴더와 작은 파일만 새로 만든다. 테스트 소유 file ID allowlist와 pre-state를 비공개 ledger에 기록한다. 기존 사용자 폴더·파일은 테스트 대상으로 선택하지 않는다.

```text
테스트 폴더/파일 생성 또는 사용자 지정 허용 확인
→ ID·pre-state 기록
→ 테스트 이동
→ API GET·독립 Drive UI 확인
→ 테스트 휴지통
→ API GET·독립 UI 확인
→ 승인된 원상복구
→ post-state·잔여 테스트 데이터 확인
```

실제 `ㅇㅎㅎ`의 개인 영상과 지정 실패 MP4는 테스트 쓰기에 사용하지 않는다. 영구 삭제·휴지통 비우기·공유 권한 확대는 금지한다. 종료 시 현재 원격 상태와 소유 allowlist를 확인한 뒤 생성한 테스트 항목만 복원·정리하고 최종 ID/상태를 기록한다. 다른 앱의 후속 변경을 자동으로 되돌리지 않는다. 필요한 OAuth 동의가 없다면 본인 동작만 요청하고 다른 작업은 계속한다.

## 14. 좋아요·시청 이력·데이터 이관

### STATE-01 — 시스템별 소유권

| 데이터 | 기본 SSOT |
|---|---|
| 원본 파일 내용·부모·휴지통·권한 | Google Drive |
| 기존 좋아요·시청 기록 | 기존 Drive appData 작성자별 상태 + 기존 병합 계약 |
| 브라우저 캐시 | 해당 계정의 복구·가속용 replica |
| 미확정 파일 작업 | 구현에서 정한 operation ledger |
| 파생 미디어 | 제거 가능한 앱 소유 cache |
| 운영 구현 상태 | source의 checkpoint/decision/release 문서 |

앱 상태를 조용하게 표시하라는 요구는 sync 삭제나 데이터 영속성 제거를 뜻하지 않는다.

### STATE-02 — appData 접근 경계

Google은 appDataFolder가 앱 전용이며 다른 Drive 앱이 볼 수 없다고 설명한다. **새 OAuth 프로젝트/클라이언트나 rclone/OpenList를 연결하면 같은 계정이므로 기존 appData를 자동으로 볼 수 있다고 가정하지 않는다.** 구체적인 클라이언트 구성 간 가시성은 실확인한다. [R12]

구조 변경 전에:

1. 기존 앱으로 state를 읽을 수 있는지 확인한다.
2. legacy 문서·writer 파일·tombstone·viewed 기록·local replica를 구분한다.
3. 새 credential 구조에서 동일 state를 읽을 수 있는지 비파괴 확인한다.
4. 불가하면 승인된 인증 세션으로 제한된 export/import 이관을 설계한다.
5. 이관 전후 항목 수·취소 기록·계정 identity·병합 결과를 확인한다.
6. 새 구조가 충분히 검증되기 전에 원본 state를 삭제하거나 빈 state로 덮어쓰지 않는다.

### STATE-03 — origin 변경

GitHub Pages에서 새 origin으로 이동하면 기존 localStorage·IndexedDB·SW·PWA 설치를 그대로 공유한다고 가정하지 않는다. 서버 인증으로 바꿨다고 기존 로컬 좋아요 cache가 자동으로 이동하지 않는다.

이관에는 사용자 재인증, 복구 가능한 state snapshot, 새 origin 읽기 확인, 기존 origin의 read-only/전환 UX, 중복 동기화 방지가 필요하다. 전체 브라우저 cache나 다른 앱 worker를 삭제하지 않는다.

### STATE-04 — 작성자별 병합과 동시 변경

기존 per-writer 저장·legacy read-only 이관·unlike tombstone·계정 세대 격리의 의미를 유지한다. 브로커를 추가했다고 두 장치가 다시 단일 파일 read-modify-write를 경쟁하게 만들지 않는다.

timestamp 충돌·장치 시계 오차가 문제가 되는지 테스트한다. 새 충돌 규칙이 필요하면 버전과 이관 규칙을 설계하고 기존 데이터를 의도치 않게 부활시키지 않는다. 단순 UI 수정을 하며 CRDT/DB 전체를 불필요하게 다시 설계하지 않는다.

### STATE-05 — 조회 부담

전경 양방향 수신은 유지하되 정상 sync 문구는 숨긴다. 내부 sync 상태는 stale/dirty/confirmed를 구분하며 실제 확인 없이 synced라고 기록하지 않는다.

동기화 최적화는 먼저 현재 호출 수·state 크기·writer 수를 측정한다. 전체 파일 목록과 appData 목록을 혼동하지 않는다. 대규모 index 갱신이 필요하면 Drive Changes API를 조건부 검토할 수 있으나, 사용자/공유 드라이브별 변경 범위와 삭제/접근 상실의 차이를 고려해야 한다. 처음부터 webhook 운영까지 추가하지 않는다. [R40]

### STATE-06 — 개인정보 보관

state export는 토큰을 포함하지 않는다. 재생 위치·좋아요·시청 기록·실패 파일명도 개인 데이터이므로 공개 Pages·공개 GitHub 이슈·외부 로그 수집기에 올리지 않는다. 예시·회귀 fixture는 합성 ID를 사용한다.

### STATE-07 — 실제 표시 이전의 시청 기록 확정을 검토한다

F-12에서 확인했듯 `app.js:openMediaSource`는 실제 재생·표시 전에 viewed 기록을 남긴다. 먼저 기존 `viewed`의 의미가 “열어봄”인지 “실제 시청”인지 결정 문서와 제품 동작으로 대조한다. **기존 의미를 확인하지 않고 새 완료 임계값을 사용자 요구인 것처럼 강요하지 않는다.**

권장 정책은 `open-requested`, `displayed/started`, `watched/completed`를 구분하는 것이다. 실제 화면도 못 보여준 파일을 자동으로 “시청 성공”으로 소비해 미시청 우선 랜덤 후보에서 밀어내지 않는다.

영상은 첫 프레임과 재생 진행, 이미지는 실제 decode/display를 기준으로 하는 정책을 우선 검토한다. 정확한 시청 시간 임계값은 기능 의미에 맞춰 정하고 제안값을 사실로 고정하지 않는다. 기존 이력을 일괄 소급 삭제하지 않는다. 변경이 채택되면 로컬·동기화·랜덤 우선순위·회귀 테스트를 함께 정렬한다.

## 15. 방해 없는 UI·제스처·접근성

### UI-01 — 정상 동작의 침묵

기본 화면에서 다음 문구/동작을 제거한다.

- `좋아요·시청 기록 동기화됨`과 정상 sync의 반복 상태 설명.
- 원본 Range·임시 디스크·OAuth 갱신·코덱 검사 등의 장문 내부 절차 설명.
- 정상 재생 위에 붙어 있는 품질 변명 배지와 닫을 수 없는 도움말 패널.
- 사용자의 행동과 무관한 반복 toast.

이 정보는 개발·문제 해결을 위해 private diagnostic 또는 설정의 상세 정보에 유지한다. 정상 spinner는 필요한 최소 범위로 쓰고, 기존 “응답을 기다립니다” 문구만 바꿔 성능 문제를 해결했다고 보고하지 않는다.

### UI-02 — 단일 chrome 표시 소유자

제목·진행바·주요 버튼·품질 상세 진입·재시도/외부 열기 보조 동작을 하나의 표시 계약으로 관리한다. `.drive-preview-actions` 같은 별도 상시 예외 레이어를 남기지 않는다.

```text
기본: hidden
PC: 맨 아래 activation zone 진입 → reveal
PC: 실제 controls/menu 조작 중 → 유지
PC: 조작 영역 이탈 → 짧은 유예 후 hide
모바일: 명시적인 하단 tap → reveal
모바일: 명시적인 바깥 tap/닫기 또는 조작 종료 정책 → hide
키보드/보조기술: 명시적인 접근 → reveal 및 focus 보존
```

pause·loadedmetadata·canplay·seek 완료·일반 중앙 mousemove는 reveal 사유가 아니다. 적절한 하단 hit area와 iPhone safe area를 테스트로 확정한다. 초기 px 값은 설계 제안이지 실제 OS gesture 영역에 대한 보장이 아니다.

### UI-03 — 경고와 실패는 숨기지 않는다

보안·권한·재생 불가·쓰기 미확정처럼 행동이 필요한 상태는 짧은 비차단 안내 또는 명시적 panel로 제공한다. panel은 재시도/취소/닫기가 가능해야 한다. 중요한 경고를 숨겨 품질 상태를 속이지 않는다.

예시 문구:

| 상태 | 기본 문구 예시 | 별도 상세 |
|---|---|---|
| 재연결 필요 | `연결을 다시 확인해 주세요.` + `연결` | OAuth reason |
| 원본 응답 지연 | `불러오지 못했습니다.` + `다시 시도`/`닫기` | 구간·upstream·대기 시간 |
| 파일 권한 부족 | `이 파일에 접근할 수 없습니다.` | 계정·scope·capability |
| 일부 이동 실패 | `3개 이동됨 · 1개 실패` | 파일별 결과 |
| 결과 미확정 | `변경 결과를 확인 중입니다.` | operation ledger |
| 품질 변환이 불가피 | 선택 시 한 번 짧게 안내 | 영상/음성/색 변경 정보 |

짧은 문구도 사실이어야 한다. 재생 자체는 가능한데 서버가 느리다는 이유로 `지원하지 않는 파일`이라고 쓰지 않는다.

### UI-04 — Google 미리보기와 외부 동작

Google iframe은 자동 복구의 정상 종료 상태에서 제외한다. 기존 기능을 남길 필요가 있으면 사용자가 명시적으로 선택하는 `Drive에서 열기` 보조 동작으로 이동한다. 외부 사이트에서 재생됐는지는 앱이 검증했다고 주장하지 않는다.

iframe을 수동 모드로 남긴다면 부모 앱의 하단 조작 영역은 iframe 위에서도 접근 가능해야 한다. iframe 내부 mouse/touch가 부모로 그대로 전달된다고 가정하지 않는다. Google 문서의 내부 패널·쿠키·controls를 CSS로 제거할 수 있다고 약속하지 않는다.

### UI-05 — PC focus와 키보드

포인터로 button/summary를 클릭한 뒤 일반 시청 문맥의 Space는 playback을 제어한다. Tab으로 의도적으로 focus한 button의 Enter/Space는 native activation을 유지한다. input/range/select/contenteditable에는 해당 편집/제어 계약을 유지한다.

숨긴 controls는 inert/접근성 상태를 일치시키되, 키보드와 VoiceOver가 명시적으로 제어를 열 수 있는 접근점을 제공한다. 단순히 전부 inert로 만들고 시각적 bottom hotspot만 남겨 비시각 사용자를 가두지 않는다. 접근점을 활성화하면 실제 보이는 controls로 focus를 옮긴다.

Tab reveal과 CSS visibility transition 사이의 지연 때문에 같은 키 입력에서 focus가 실패하지 않게 한다. 이전 버전에서 다룬 문제를 재발시키지 않는다.

### UI-06 — 단일 gesture owner

모서리 back, media swipe, seek, long-press, 브라우저/OS gesture는 pointer/touch sequence 시작부터 소유권을 분리한다.

- edge에서 시작한 입력이 취소되더라도 나중에 previous-video로 해석되지 않는다.
- OS가 취소 불가능한 이벤트를 소유하면 custom transition을 commit하지 않는다.
- 두 번째 손가락·세로 scroll intent·화면 변경·blur·visibility 전환에 pending gesture를 정리한다.
- 완료·취소 콜백은 generation/transition identity로 정확히 한 번만 적용한다.
- player back 한 번은 player만 닫고 다음 back은 적합한 라이브러리 이력을 따른다.
- player adapter를 교체해도 동일한 event가 새 엔진과 예전 엔진에 모두 전달되지 않는다.

### UI-07 — 길게 누르기

카드 범위에서 image drag·selection·callout 충돌을 억제한다. 입력창까지 전역 `user-select:none`으로 막지 않는다. 성공한 hold의 release click은 소비해 영상이 동시에 열리지 않게 한다. native context menu 취소와 long-press selection의 타이밍을 실기기에서 확인한다.

### UI-08 — 전체화면·회전·safe area

앱 소유 전체화면과 OS native video fullscreen은 다를 수 있다. OS가 소유한 controls를 앱이 완전히 숨길 수 있다고 주장하지 않는다. 선택한 화면 모드에서 하단 전용 정책이 실제 충족되는지 검사하고 제약을 기록한다.

세로/가로·회전 후에도 close/seek/menu가 안전 영역 밖으로 잘리지 않고, 영상은 필요한 비율·회전 정보를 유지한다. 접근 가능한 클릭 영역과 시각 크기를 분리해 너무 작은 버튼으로 시청 방해를 줄이려 하지 않는다.

## 16. 보안·개인정보·의존성

### SEC-01 — 비밀정보 경계

- Google token·client secret·cookie를 공개 정적 JS/HTML에 내장하거나 URL·Git·진단 로그에 기록하지 않는다. B-auth가 짧은 access token을 인증된 브라우저 메모리에만 전달하는 선택은 AUTH-09의 별도 보안 계약을 따른다. refresh token·client secret의 client 전달은 금지한다.
- 공개 client의 속성과 server secret을 혼동하지 않는다. 현재 웹/PWA 배포에 맞는 OAuth 유형을 사용한다. 네이티브 client를 웹에서 흉내 내지 않는다. [R04][R05]
- OAuth code와 media capability는 로그에서 정제한다.
- native subprocess 인자·환경·stdout/stderr가 사용자 도구 기록에 노출되는지 고려한다.
- 예시 설정에는 placeholder만 넣고 실제 credential은 OS/서버 보안 저장 경로를 사용한다.

### SEC-02 — 서버 노출

rclone HTTP serving은 인증 설정 없이 노출될 수 있다. 기본 실행을 외부 공개 서비스로 바로 연결하지 않는다. [R20]

B 배치에서 확인할 항목:

```text
기본 바인딩·TLS·접근제어
admin/health/diagnostic endpoint 노출 범위
세션 fixation·CSRF·Origin 검증
CORS의 정확한 allowlist
파일 ID별 권한 검증
미디어 capability의 범위·만료·재사용
rate limit·요청 크기·작업 수 제한
reverse proxy streaming buffering·timeout·log redaction
```

API 응답을 캐시하는 CDN이 계정별 미디어를 공유하지 않게 한다. 넓은 `Access-Control-Allow-Origin:*`와 credential 허용을 임의로 조합하지 않는다.

### SEC-03 — SSRF·경로·명령 주입

- 공개 endpoint에 임의 URL/path/FFmpeg 옵션을 받지 않는다.
- Google의 검증된 fileId를 server-side route로 변환한다.
- 파생 파일 이름은 내부 식별자로 만들고 상대 경로 탈출·심볼릭 링크·기존 원본 덮어쓰기를 차단한다.
- subprocess는 shell 문자열이 아닌 검증된 인자 배열로 실행한다.
- 미디어 parser는 손상 입력·비정상 frame size·리소스 폭주를 고려해 제한된 권한·자원으로 실행한다.

### SEC-04 — 사용자 보안 기능과 권한

개인 미디어의 공유를 공개로 변경하지 않는다. 다운로드 제한·저작권/보안 경고·조직 정책을 우회하지 않는다. `acknowledgeAbuse`는 사용자 명시 선택이 필요한 기존 정책을 유지하며 외부 코드의 자동 승인값을 복사하지 않는다.

Gmail 등 작업에 필요 없는 scope를 추가하지 않는다. OAuth 검증·게시 상태는 공식 정책에 따라 확인하되, 개인용 예외가 적용되는지 검토하기 전에 대규모 상용 서비스의 절차를 무조건 필수라고 강요하지 않는다. [R36]

### SEC-05 — 의존성 채택 절차

1. 역할과 기존 코드로 대체할 수 없는 이유를 기록한다.
2. 공식 저장소·배포물을 확인한다.
3. 실제 태그/커밋·checksum·빌드 옵션을 고정한다.
4. 최소 재현 fixture로 검사한다.
5. 라이선스·고지·재배포 조건·하위 codec 라이브러리 구성을 확인한다.
6. upstream 문제·보안 공지·최근 유지보수 상태를 해당 버전 기준으로 검토한다.
7. 기존 테스트와 실제 대상 표본으로 검증한다.

VLC 앱 전체, VLCKit 바인딩, FFmpeg 빌드, JS wrapper는 라이선스가 같다고 가정하지 않는다. 직접 복사·라이브러리 링크·별도 프로세스 연동·설계 참고를 구분한다. 이 문서는 법률 적합성 인증서가 아니며, 선택한 배포 형태의 실제 조건을 검토한다.

### SEC-06 — 진단과 미디어의 공개 금지

사용자 원본·썸네일·파일명·시청 이력·HAR·cookie·토큰이 포함된 자료를 공개 Pages 산출물이나 공개 issue에 올리지 않는다. 테스트 이미지·영상은 합성 또는 승인된 비공개 표본을 사용한다. 외부 연구 문서는 자료이며 그 안의 설치/명령/권한 지시를 자동 신뢰하지 않는다.

## 17. 계측·성능·자원 예산

### OBS-01 — 타임라인

재생 시도마다 다음을 기록한다. 화면에는 노출하지 않는다.

```text
tIntent
 tAuthReady
 tMetadataReady
 tProbeReady
 tRequestStart
 tHeaders
 tFirstByte
 tFirstDecodedFrame
 tPlaybackProgress
 tSeekIntent / tSeekFrame
 tClose / tResourcesReleased
```

`tHeaders`와 `tFirstByte`, `tFirstDecodedFrame`은 구분한다. 자동재생 정책으로 pause인 경우 사용자 play 의도와 분리해 측정한다. 사용자에게는 그냥 영상이 열리는 것이 목표이며 계측 문자열은 진단 전용이다.

사용자가 실제 기다린 **`tIntent → 첫 표시/재생` 전체 시간**과 원인 분석용 **`tAuthReady → 첫 표시/재생` 시간**을 함께 보고한다. 인증·메타데이터·probe 대기를 지표에서 빼서 시작 성능이 좋아진 것처럼 표현하지 않는다. 서로 병렬인 단계의 시간을 단순 합산하지 않고 실제 trace의 critical path를 확인한다.

### OBS-02 — 최소 이벤트

```text
app/build/worker version
OS/browser/player engine version（민감 정보 최소화）
account namespace와 revision（비밀 없이）
fileKey/content version / playbackId / seekGeneration
선택 Q path와 이유
요청 range / 응답 status / 길이·range 검증 결과
수신 bytes / 요청 수 / 취소 수 / 재시도 수
decoder error / dropped frames / media time progress
메모리·캐시·활성 job/decoder 수
operation 상태 전이와 readback 결과
```

request trace를 무제한 쌓지 않는다. 로컬 ring buffer·보관 상한·오류 시 선택 export를 우선한다. 로그를 많이 찍기 때문에 재생 성능이 나빠지는 구조를 피한다.

### OBS-03 — 성능 목표는 측정 조건과 함께

아래 수치는 **초기 설계 목표/조정 가능한 예산**이며 Google나 브라우저의 보장이 아니다. 실제 baseline·장치·호스트·네트워크에 맞춰 rationale과 함께 확정한다.

| 지표 | 초기 목표 | 측정 조건/주의 |
|---|---|---|
| Q0 첫 프레임 p95 | 약 5초 이내 | 인증 준비 완료, cold media cache, 안정된 지정 네트워크 |
| warm resume 첫 프레임 p95 | 약 2초 이내 | 같은 파일 버전·유효 cache |
| Q0 정상 seek 재개 p95 | 약 3초 이내 | target 10/50/90%, 인증/네트워크 상태 기록 |
| headers 대기 판단 | 약 10초 | 고정 전체 stream timeout과 구분 |
| 전경 body/frame 완전 무진행 판단 | 약 15초 | pause·hidden·retry-after 제외 |
| 초기 재생 불가의 조작 가능한 결과 | 약 30초 내 | server가 더 긴 retry-after를 요구하면 취소 가능한 대기 상태를 제공 |
| close 이후 불필요 작업 정리 | 짧은 유예 내; 예: 2초 목표 | 실제 비동기 프로세스 종료·공유 lease 확인 |
| 같은 계정 전경 상태 전파 | 예: 20초 내 목표 | 기존 약 15초 mock 측정과 실제 Google 측정 분리 |
| 데이터 손상·잘못된 파일 쓰기 | 0건 | 성능을 위해 완화할 수 없는 correctness gate |

5개 시도만으로 p95를 안정적으로 측정했다고 하지 않는다. 초기 탐색은 소수 반복으로 하되, 최종 분포는 충분한 반복 횟수·실패·timeout을 포함해 보고한다. 권장 시작점은 대표 시나리오 20회이며 통계적 불확실성도 함께 기록한다.

### OBS-04 — 자원 예산

호스트·iPhone이 확인되지 않았으므로 무근거 고정 MiB 수치를 제품 상수로 확정하지 않는다. 구현 초기에 다음 budget을 명시한다.

| 자원 | 예산을 결정할 관찰 | 불변식 |
|---|---|---|
| 브라우저 미디어 메모리 | 실제 큰 파일·연속 전환·기기 메모리 | 전체 file size에 비례한 전량 적재 금지 |
| server cache | 가용 disk·시청 패턴·전송 비용 | 상한·LRU/lease·부분파일 정리 |
| 동시 source request | 긴 영상 시작·seek·quota | 무제한 fan-out 금지 |
| FFmpeg/native jobs | 실시간 처리율·CPU/GPU·열 | 이전 시도 job 누적 금지 |
| 썸네일/metadata | 가시 영역·첫 프레임 지연 | 현재 재생 우선 |
| 진단 로그 | 실패 분석에 필요한 최소 이벤트 | 비밀·개인 원본 제외, bounded retention |

현재 조사에 없는 하드웨어 능력을 가정하지 않는다. 오래된 브라우저 제한 수치를 영구 하드코딩하기보다 capability·측정·안전한 fallback을 결합한다.

### OBS-05 — 회귀 비교

동일 파일 버전·같은 장치·같은 네트워크 조건에서 기준 버전과 후보를 비교한다. cold와 warm을 혼합하지 않는다. 새 서버에서 네트워크 경로가 바뀌면 이를 표시한다.

첫 프레임만 빨라지고 seek 실패·화질 저하·배터리 과사용이 증가한 경우 전체 개선이라고 보고하지 않는다. 원본 품질·실제 성공률·지연·자원 비용을 함께 비교한다.

## 18. 재현 실험과 장애 주입

### EXP-01 — 관측의 우선순위

아키텍처를 바꾸기 전에 최초 실패 지점을 찾는다. 다만 root cause를 찾겠다고 안전한 즉시 수정（상시 안내 제거·명백한 성공 추정 제거）까지 미루지 않는다. 각각 독립 테스트와 변경 범위를 유지한다.

### EXP-02 — 판별력이 높은 비교 실험

| 실험 | 같은 조건에서 바꾸는 것 | 판별 |
|---|---|---|
| E01 | 같은 파일을 현행 SW 경로와 독립 API reader로 | 앱 전송 문제 vs upstream 문제 |
| E02 | 같은 원본을 browser와 native engine으로 | 전송 문제 vs codec/container 문제 |
| E03 | 같은 stream을 container만 변경 | container 문제인지, 재인코딩이 정말 필요한지 |
| E04 | 영상 유지·음성만 변환 | 음성 codec 때문에 전체 영상 변환되는지 |
| E05 | 동일 파일 앞/중간/끝 range | index·suffix·offset 처리 문제 |
| E06 | 유효 API 토큰 + third-party cookie blocked | OAuth와 Google iframe 로그인 경로 분리 |
| E07 | 같은 파일 ID의 PATCH 응답 뒤 독립 GET | UI만 변경인지 실제 remote commit인지 |
| E08 | 같은 파일 클라우드 GET vs Drive 웹 vs G: | 다른 계정/ID와 desktop sync 지연 구분 |
| E09 | 이전/새 앱과 SW 조합 | cache/update protocol 혼입 |
| E10 | 같은 코드·파일에서 전경/백그라운드 복귀 | 타이머 중지·세션·OS 제약 |

rclone/VLC 비교가 정상이라는 이유만으로 그 프로젝트를 전부 도입하지 않는다. 비교 실험은 결함 계층을 찾는 증거다.

### EXP-03 — synthetic fixture 확장

현재의 짧은 fixture만으로 충분하지 않다. 다음을 생성·확보한다. 사용자 원본을 변조하지 않는다.

- faststart MP4와 tail-index MP4, MOV, fragmented MP4.
- 지원/비지원 audio 조합, 무음·다중 음성, 회전·VFR 표본.
- MKV·AVI·WebM의 실제 대표 codec 조합.
- header는 정상이나 body가 멈춤, 느린 첫 바이트, 중간 끊김.
- 206의 길이·범위 불일치, 유효하게 짧은 부분 응답, 200 sequential, 416.
- 2 GiB·4 GiB 경계를 넘는 offset/size의 sparse 또는 합성 range fixture.
- first frame만 나오고 진행이 멈춤, seek 후 잘못된 위치, 오디오 누락.
- 이미지 alpha·회전·animated GIF/WebP·큰 해상도.

큰 offset 테스트를 위해 실제 4 GiB 파일을 메모리에 만들어 올릴 필요는 없다. correctness fixture와 실제 대용량 성능 검사를 구분한다.

### EXP-04 — 인증 장애

유효 token→만료, 같은 문자열의 새 revision, 늦은 401, 동시 다수 요청, 팝업 취소, offline 갱신 실패, 계정 전환 중 응답, grant 철회, refresh token 없는 응답을 테스트한다.

mock refresh 성공이 실제 OAuth 정책하의 성공을 증명하지 않는다. 실제 계정에서는 승인된 정상 만료를 기다리는 시나리오와 앱의 인위적 clock/state 변형 테스트를 분리한다. 후자를 실제 Google 만료라고 기록하지 않는다.

### EXP-05 — 쓰기 장애

PATCH가 서버에 적용된 뒤 응답 유실, 적용 전 단절, 일부 항목 403/429, 마지막 항목 실패, 계정 전환, reload, 프로세스 재시작, 외부 앱의 부모 변경, 중복 operationId, duplicate filename, shortcut을 테스트한다.

정확한 파일별 결과·pending 복구·원격 readback·안전한 재시도가 핵심이다. mock handler가 어떤 PATCH든 200으로 응답하게 만들어 잘못된 부모 처리까지 통과시키지 않는다.

### EXP-06 — UI·수명주기

PC 320폭부터 큰 desktop, iPhone 세로/가로·safe area·PWA에서 hidden/revealed/paused/error/menu/fullscreen 상태를 검사한다. 최소 viewport 통과와 실제 iPhone touch behavior를 구분한다.

50회 연속 파일 전환·back 취소/재시작·seek·close를 반복해 활성 decoder/job/객체 URL/타이머·listener가 누적되는지 확인한다. 오류가 없었다는 콘솔 결과만 아니라 리소스 수와 상태도 확인한다.

### EXP-07 — 안전한 실패 증거

실패 테스트를 삭제하거나 예상값을 느슨하게 바꿔 통과시키지 않는다. 요구 자체가 바뀌면 기존 contract의 폐기 이유와 새 테스트가 더 정확히 검사하는 조건을 기록한다.

도구·네트워크·기기가 없으면 `blocked/unverified`로 기록한다. 없는 결과를 상상하거나 브라우저 mock으로 대체한 뒤 동등한 검증이라 하지 않는다.

## 19. 구현 작업 패키지와 의존 순서

### 19.1 실행 방식

기존 작업을 보존하고 별도 작업 브랜치에서 작은 검증 단위로 진행한다. 단순 UI 수정과 아키텍처 변경을 한 덩어리로 커밋해 원인 추적을 어렵게 만들지 않는다. 요구를 변경하지 않는 범위에서 더 단순한 구현을 선택할 수 있으며 이유를 기록한다.

“가장 효과적인 플랜”은 가능한 모든 기술을 먼저 만드는 것이 아니라 **결정을 바꿀 정보부터 확보하고, 실패를 가장 많이 제거하는 경로부터 완성하는 계획**이다.

### 19.3 구체적인 작업 순서

**첫 번째 작업 묶음:** 현재 버전과 사용자 실패가 같은 코드인지 확인하고, 원본 경로 최초 실패 trace·동일 파일 ID의 쓰기 readback을 확보한다. 별도 패널과 정상 문구는 작은 패치로 분리한다.

**두 번째 작업 묶음:** 인증과 data path를 분리해 06장 방향을 검증한다. 직접 range·필요 native/remux 비교와 최소 무료 B-auth 실험을 수행한다. 01장 범위의 후보 설정·배포는 진행하되 본인 로그인·약관·비용 한계를 임의로 넘지 않는다.

**세 번째 작업 묶음:** 인증·Drive repository·operation 상태와 원본 critical path를 작은 end-to-end 경로로 통합한다. B-auth가 갱신을 소유해도 source 전달은 SW에 남을 수 있다. 중복 refresh/recovery만 제거하고 실제 선택한 역할 경계와 호출자를 함께 검사한다.

**네 번째 작업 묶음:** 기본 Q0를 유지하면서 실제 필요한 Q1/Q2/Q3만 추가한다. 전체 코덱 행렬과 rare format을 검사한다. source 유출·캐시 혼합·resource cleanup도 같은 인터페이스의 테스트로 묶는다.

**마지막 작업 묶음:** 실제 Google·iPhone·일회용 테스트 작업을 검증한다. 실제 검사는 가능하면 앞 단계부터 수행하고 마지막에 종합한다. 검증 후보와 rollback을 준비한 뒤 별도 운영 전환 승인을 요청한다. 미검증은 그 항목의 상태로 남기며 구현 전체를 계획 단계로 되돌리지 않는다.

### 19.5 병렬 워커 사용 시

기본은 주 워커 하나다. 도구와 현재 세션 범위에서 별도 유료 계약·외부 실행 없이 가능한 독립 읽기·고정 SHA 검토만 필요할 때 사용한다. 추가 쓰기 워커는 파일·인터페이스·외부 자원 소유권이 분리되고 실행 범위가 확인된 경우에만 사용한다. 여러 워커가 같은 거대한 `app.js`를 동시에 수정하지 않는다.

| 역할 | 병렬로 할 수 있는 일 | 통합 규칙 |
|---|---|---|
| 주 워커 | 공통 계약·상태·실제 통합·release 판단 | 공유 파일 편집 소유자 |
| 조사/QA 워커 | 공식 자료 검증·fixture·실기기 체크리스트 | 결과는 가설/관찰 분리, production 변경 금지 |
| auth/source 워커 | 합의된 독립 모듈과 단위 테스트 | public 인터페이스 먼저 확정 |
| UI/mutation 워커 | 합의된 UI 또는 작업 계층 | 원본 쓰기 검증은 승인 범위만 |

도구가 없으면 단일 워커로 순서대로 진행한다. 사용량·시간 때문에 검증 범위를 줄였으면 명시하고, 협업 수 자체를 품질의 증거로 삼지 않는다.


### 19.6 기존 세부 작업 ID를 새 조건에 맞게 계속한다

현재 goal에서 이미 `V2-00A`~`V2-10B` 하위 표를 만들었다. 그 표를 우선 재사용하고 아래 변경을 반영한다.

| 작업/분기 | 이번 실행에서의 판단 |
|---|---|
| `V2-00A`, `V2-01A` | 기준 보고/집중 fixture가 현재 코드와 일치하면 재사용. 새 목표 지도 반복 작성 금지 |
| `V2-01B` | 아직 없으면 최소 correlated trace 완료. 이미 유효한 진단이면 중복 시스템을 만들지 않음 |
| `V2-01C` | 표본 경로는 제공됨. 실제 ID·version 확인 후 최초 실패 trace로 진행 |
| `V2-02A/B` | 제품 코드 수정 승인됨. 상시 패널/정상 문구는 architecture 결론과 독립 패치 |
| `V2-03A/B/C` | data comparator와 auth 실험을 분리. C 배포/상시 서버 재질문은 제외. native는 비교만 |
| `V2-04A/B` | 필요 B-auth·실제 장기 세션·PWA 복귀 검사. 08 이관 설계를 변경 전에 수행 |
| `V2-05A/B` | ledger synthetic와 새 테스트 ID의 live readback·복구를 이어 수행 |
| `V2-06A/B`, `V2-07A/B` | 우선 지정 표본의 연결 동작을 만든 뒤 장시간·rare type·Q 경로로 확대 |
| `V2-08A` | 이미 이관 허용. appData 접근·snapshot 검증 선행, 기존 데이터 삭제 금지 |
| `V2-09A/B`, `V2-10A` | 기존·추가 인수 검사, 고정 후보 리뷰·안전한 검증 배포 |
| `V2-10B` | production/main/push 승인 대기. 코드/후보 준비와 별도 상태 |

이 표는 새 SSOT가 아니라 기존 goal을 현행화할 입력이다. 실제 완료 상태는 소스·증거를 보고 정한다. 현재 입력이 해소한 blocker만 닫고 새 접근·기기·서비스 조건은 별도 unknown으로 기록한다.

### 19.7 작업 단위와 전체 완성의 연결

작업 하나는 “인증 전부”, “파일 하나”, “문서 한 장”이 아니라 관찰 가능한 동작 또는 판별 질문이다. 하나의 refresh 동시성, 하나의 range→frame 경로, 하나의 uncertain mutation 확인처럼 구현·호출자·회귀까지 닫을 수 있게 한다. 자세한 복구·인수 운영은 26장을 적용한다.

공통 계약을 바꾼 단계에서 통합 검사를 한다. 마지막 WP에 처음으로 auth/reader/player/operation을 합치는 방식은 금지한다. 개별 작업이 작다는 이유로 최종 형식·실기기·동시성 요구를 잘라내지 않는다.

### 20.7 실제 기기 최소 행렬

필수 환경은 실제 PC 브라우저, **사용자가 보고한 iPhone Chrome 탭과 홈 화면 PWA**, 실제 iPhone Safari 탭이다. 첫 비교는 PC/Chrome 탭/PWA로 하고 Safari도 회귀·격리 검사에 포함한다. 모델/OS/브라우저 버전은 실행 시 기록한다. Windows WebKit과 iPhone viewport는 대체 증거가 아니다.

실제 계정 테스트는 동일 계정 두 기기와 계정 변경 시나리오를 구분한다. 테스트에 계정 접근 권한이 없으면 staging/mock 결과만 남기고 live gate는 blocked로 유지한다.

실제 장시간 테스트에는 적어도 초기 재생, 만료 경계의 추가 요청, 중간/끝 seek, background→foreground 복귀가 포함돼야 한다. 정상 API 인증이 유지되는지와 Google iframe 쿠키 상태를 별개로 기록한다.

## 21. 배포·서비스 워커·롤백

### REL-01 — 배포 권한과 구조

이번 실행은 무료·안전한 **후보 검증용 배포**를 허용한다. `main` 병합·원격 push·기존 production 서비스 교체는 아직 승인되지 않았다. 고정 후보·실기기 인수·복구 계획을 만든 뒤 마지막에 그 승인만 요청한다. B-auth/선택 relay가 있으면 기존 정적 Pages 명령만으로 그 기능까지 배포되는 것이 아니다.

현재 기록상 정적 경로는 `scripts/publish-pages.cjs`와 공개 allowlist 12개 파일을 `gh-pages`에 게시하는 구조다. 과거 whole-repository workflow를 무심코 켜지 않는다. 새로운 의존성/정적 자산이 필요한 경우 allowlist를 명시적으로 검토한다.

### REL-02 — 실제 선택된 경로에 따라 SW 역할을 정리한다

| 선택한 경로 | SW 계약 |
|---|---|
| 현행 A 직접 reader | client별 token·revision·Range·abort의 정확성 보강 |
| B-auth + 직접 reader | 원본 전달 역할 유지 가능. credential은 B-auth와 연결된 한 공급 경로를 사용. 옛 GIS refresh loop와 경쟁 금지 |
| 인증된 같은 origin media relay | 같은 media 요청에 과거 Google proxy를 다시 적용하지 않음 |
| static shell | 공개 자산만 캐시. 로그인/API/token/개인 미디어는 shell cache에서 제외 |

- client/account 세대가 다른 credential을 공유하지 않는다.
- old/new worker와 프런트·B-auth의 프로토콜 버전 불일치를 감지하고 안전한 갱신/재연결을 제공한다.
- 앱 scope의 해당 cache만 정리한다. 다른 앱·사용자 전체 저장소·기존 이관 전 state를 삭제하지 않는다.
- 후보 origin에서는 실제 임시 API/미디어에 접근제어를 적용한다. “개발 서버”라는 이유로 인증을 제거하지 않는다.

### REL-03 — staged rollout

최소 release 단계:

```text
고정된 source/build/protocol 기준
→ 전체 자동·브라우저 QA
→ staging 실제 계정/기기 확인
→ 승인된 production publish
→ 실제 serving SHA·asset·API·media smoke
→ 모니터링·known-issues·rollback readback
```

feature flag를 두는 경우 계정/배포별 owner를 명확히 하고, 사용자가 실패할 때마다 old/new 경로를 랜덤 전환하지 않는다. 되돌릴 수 있게 한다는 이유로 불안정한 두 구현을 무기한 유지하지 않는다.

### REL-04 — 배포 후 검사

- 실제 제공되는 HTML/JS/CSS/worker와 source SHA·버전·cache 정합성.
- B에서는 backend build/protocol과 브라우저 build의 호환성.
- private memory/tests/qa/credential/캐시·미디어 원본이 공개 artifact에 포함되지 않는지.
- cold startup, 기존 설치 업데이트, offline shell, 실제 원본 재생·하단 controls·로그인·승인된 테스트 파일 작업.
- production에서 fixture/demo interception이 활성화되지 않는지.
- production URL에서 실제 계정 smoke가 없으면 demo smoke였다고 명시.

### REL-05 — 롤백과 데이터

Git 강제 push·history 삭제로 되돌리지 않는다. 알려진 정상 source/공개 tree를 새로운 검증된 배포로 반영한다. schema/작업 기록/캐시 프로토콜의 역호환을 먼저 확인한다.

롤백은 잘못된 원격 파일 작업을 자동으로 되돌리는 권한이 아니다. 실제 파일의 복구는 저장된 operation 의도·원격 현재 상태·사용자 승인에 따라 별도로 수행한다. 외부 앱이 후속 이동한 파일을 옛 부모로 일괄 복구하지 않는다.

원본과 상태 snapshot을 보존한다. 새 구조에서 쓴 좋아요를 옛 앱이 빈 state로 덮어쓰지 않도록 rollback read path와 schema를 검증한다.

| G1 재현·분류 | load/auth/codec/write 최초 실패의 증거 | 가설 상태로 표시, 구조 선택 실험 우선 |
| G2 구조 결정 | 채택안의 호스트·비용·권한·데이터 이관 확인 | 승인된 기존 경로 개선은 계속, 차단 분기만 보류 |
| G3 구현 정확성 | 테스트·범위·원본 안전·상태 소유권 | 설명되지 않은 실패를 둔 release 금지 |
| G4 통합·자원 | 실제 browser input·형식·seek·cleanup·보안 | 수정·재검증 |
| G5 실제 환경 | iPhone/실제 Google/승인된 remote write | 없으면 최종 인수 미완료; mock으로 승격 금지 |
| G6 운영 반영 | 별도 main/push/production 승인과 served proof | 이번 후보 구현 완료와 운영 승인 대기를 구분 |
| G7 인수인계 | 원인·결정·제외·증거·복구·남은 항목 | 다음 워커가 현재 상태를 오해하지 않게 보완 |

### 22.2 하드 게이트와 성능 목표의 구분

원본 손상, 잘못된 파일 수정, credential 유출, 계정 데이터 혼합, 무한 재시도, 가짜 성공은 완화할 수 없는 실패다.

몇 초의 first-frame 목표는 실제 환경에 맞춰 조정 가능한 성능 목표다. 그러나 조정 이유와 사용자 체감 trade-off 없이 목표값만 느슨하게 바꿔 통과시키지 않는다. 모든 요구를 원래 수준으로 다시 대조한다.

### 22.3 최종 보고 형식

```text
1. 현재 완료 상태: 구현 / 자동 검증 / 실제 검증 / 운영 배포를 구분
2. BUG-01~08 각각: 원인, 증거, 수정, 재검증, 남은 제한
```

### 22.5 중단 기준

핵심 가설이 증거로 지지되고 요구별 테스트·실제 관찰이 충분하면 조사/리팩터링을 종료한다. 더 조사해도 의사결정이 바뀌지 않는 영역의 프로젝트·논문·라이브러리 목록을 계속 늘리지 않는다.

## 24. 새 세션이 지금 수행할 행동과 보고

### 24.1 첫 행동은 이전 작업 재개다

1. 00·01장의 최신 입력과 범위를 읽고 실제 프로젝트 root/source·branch/HEAD/status/diff·실행 중 편집을 확인한다. 다른 사람의 미커밋 변경을 보존한다.
2. 현재 goal·CHECKPOINT·결정·QA 기록을 대조한다. 본 통합 명세의 실제 읽기 위치를 연결하고 이전 두 파일과 과거 plan-only 제한을 현행화한다.
3. `A-005~007`와 작업표의 해소된 blocker를 갱신한다. 지정 표본·기기 참여·실쓰기 조건을 이미 받았다는 사실을 잊고 반복 질문하지 않는다.
4. 유효한 진단이 없으면 `V2-01B` 최소 trace를 완료하고 지정 MP4의 실제 ID·version·최초 실패로 이어간다. 필요한 sample/경로 승인이 있으면 그것만 요청한다.
5. 원본 reader와 B-auth의 판별을 구분하고, 한 파일의 인증→원본→frame→seek→close를 일찍 연결한다. 상시 UI 패널/정상 문구는 별도 작은 패치로 정리한다.
6. 승인된 READY 작업이 있으면 구현·검증·기록 후 다음 작업으로 계속한다. 첫 진단이나 새 계획을 만들었다는 이유만으로 최종 답변을 내고 멈추지 않는다.

### 24.2 이번 보고는 실제 전진을 보여야 한다

진행 보고는 길게 반복하지 않고 다음을 증거와 함께 남긴다.

- 지정 MP4의 확인된 식별·probe·최초 실패와 비교 결과.
- 변경한 동작, 실패 전후 검사, 정확한 코드/환경/증거 위치.
- 인증 구조와 data path의 선택 근거·무료 운영·이관 확인.
- 실제 원본 재생·기기별 결과와 아직 필요한 사용자 조작.
- 일회용 테스트 ID의 실제 remote write·readback·복구 상태.
- 다음 READY 행동 또는 해당 분기의 정확한 차단점.

가능한 승인 작업을 모두 수행한 뒤에 최종 후보 보고를 한다. “계획 수립 완료”를 “제품 구현 완료”로 대체하지 않는다. 전체 BUG/GOAL/QA에 연결된 상태와 고정 후보를 제시하고 운영 전환 승인만 별도로 요청한다.

### 24.3 사용자 본인 조작 요청 형식

```text
필요한 조작: 한 가지 본인 행동 또는 2~3개 기기 동작
목적: 이 행동으로 판별/완료할 정확한 조건
대상: 실제 후보 주소·앱 버전 또는 승인할 경로
비용·데이터 영향: 없음 또는 구체적 설명
확인할 결과: 화면/오류/소요 시간/필요한 비공개 캡처
```

코덱·CORS·A/B/C 같은 설계 판단을 사용자에게 다시 맡기지 않는다. 도구로 알 수 있는 정보는 읽는다. 로그인·2FA·서비스 약관·경로 승인·실제 iPhone 조작처럼 본인 행동만 요청한다. 사용자가 바로 테스트 가능하다고 했지만 워커가 자동으로 폰을 제어할 수 있다고 추정하지 않는다.

### 24.4 최종 운영 승인 전에 준비할 것

고정 source/build/protocol, 독립 diff 검토, 기존/추가 테스트 상태, 지정 파일과 실제 기기의 인수 증거, source/origin/OAuth/state 이관 상태, 비용/한도, private build 제외, 업데이트·rollback을 정리한다. 배포 승인을 얻기 전에 해야 할 승인된 개발·후보 검증을 미완성 상태로 떠넘기지 않는다.

## 26. 장기 구현·컨텍스트 복구·독립 검토 규약

이 장은 실행 규약 v1.0의 활성 운영 계약을 통합했다. 과거의 착수 단계 전용 프롬프트는 제거했으며, 권한은 01장 하나가 소유한다.

### 26.1 권장 운영 방식

**하나의 총괄 목표를 유지하면서, 동시에 편집 중인 핵심 작업은 하나로 제한한다. 각 작업은 재현→변경→검증→복구 기록까지 닫는다. 압축은 허용하지만, 압축된 대화만을 작업 상태의 유일한 근거로 삼지 않는다.**

작업 분할, 새 채팅, 병렬 에이전트는 서로 다른 선택이다. 단계별 구현을 위해 매번 새 채팅을 만들 필요는 없고, 새 에이전트를 여러 개 쓰는 것이 자동으로 품질을 높이지도 않는다. 한 총괄 세션에서 여러 검증 단위를 순차 처리하고, 필요할 때만 독립 조사·검토를 별도 컨텍스트에 위임하는 것을 기본안으로 삼는다. [EP01][EP02][EP05][EP06]

이 운영 방식이 해당 프로젝트에서 다른 방식보다 몇 퍼센트 우수한지는 측정하지 않았다. 아래는 공식 지침·공개 실험을 현재 명세에 적용한 설계 제안이지, 특정 Codex 모델의 비교실험 결과가 아니다.

### 26.2 전체 명세와 현재 작업을 분리한다

본 통합본의 19장과 기존 goal은 WP-00~WP-10 및 세부 작업을 연결한다. 20장은 인수 테스트, 23장은 기록 소유권, 24장은 실제 재개 행동이다. 기존 번호와 검증을 유지하고 사용자 최신 조건만 반영한다.

처음에는 전체 요구·제약·의존관계를 파악해 요구 ID가 빠지지 않는 작업 지도를 만든다. 이후 매 작업에는 다음 내용만 집중적으로 읽는다.

- 원본 명세의 공통 불변 조건과 이번 작업에 해당하는 절.
- 이번 작업이 의존하는 채택된 결정·인터페이스.
- 현재 Git 상태, 관련 소스·호출자·테스트.
- 가장 최근 검증 증거와 아직 해결하지 않은 반례.

상세 명세를 짧게 잘라 요구를 삭제하지 않는다. 반대로 전체 상세 장, 모든 소스, 모든 성공 로그를 매번 대화에 재출력하지 않는다. 전체 요구는 접근 가능한 원문에 보존하고, 현재 판단에 필요한 내용을 불러온다. 상위 요구와 실제 구현이 어긋나면 관련 원문을 다시 읽는다. [EP03][EP04]

`AGENTS.md`는 전체 명세를 복사하는 장소가 아니라, 원문·실행계획·복구 기록을 찾는 짧은 입구로 쓴다. 기존 규칙을 무작정 덮어쓰지 않는다. Codex의 AGENTS 탐색에는 프로젝트 경로와 크기 제한이 있으므로 파일을 만들어 놓았다는 사실만으로 전부 읽힌다고 가정하지 않는다. [EP07]

### 26.3 기존 기록의 소유권을 재사용한다

| 정보 | 우선 재사용할 위치/방식 | 중복 방지 |
|---|---|---|
| 제품 목표·전체 계약 | 이 v3.0 통합 명세의 확인된 로컬 위치 | 이전 v2.0과 규약 v1.0은 역사·출처, 활성 입력은 이 파일 한 부 |
| 작업 패키지·진행·요구/테스트 연결 | 현재 프로젝트에서 이 목표를 소유하는 실행계획/goal 문서 | 기존 소유 문서를 먼저 찾음. 없을 때만 실행계획 하나 추가 |
| 재시작 진입점 | `memory/CHECKPOINT.md` | 전체 로그를 복사하지 않고 현재 작업·정확한 참조·다음 행동만 표시 |
| 채택/기각 결정과 이유 | `memory/DECISIONS.md` | 실행계획은 결정 ID로 연결. 변경 시 과거 기록을 지우지 않음 |
| 차단된 승인·실기기·가설 | `memory/OPEN-QUESTIONS.md` | 담당자, 영향받는 분기, 다음 판별 검사 명시 |
| 실행 증거 | 기존 `tests/`, `qa/`, `qa/<run-id>/` 구조 | 코드 버전·환경·결과를 연결. private 자료는 공개 산출물에서 제외 |

`PLANS.md`, `TASKS.md`, `STATUS.md`, `PROGRESS.md`, `HANDOFF.md`, JSON 작업판을 한꺼번에 신설하지 않는다. 파일 수가 아니라 정보의 소유자와 복구 가능성이 중요하다.

첨부가 작업 파일 시스템에 자동으로 존재한다고 가정하지 않는다. 이 통합 파일의 실제 접근 위치·문서 버전·해시를 확인하고, 재시작 후에도 읽을 수 있도록 00.6의 한 부 보존 규칙을 따른다. 이전 두 파일 또는 이전 채팅을 추가로 받아야만 시작할 수 있는 구조가 아니다. 첨부 자체에 접근할 수 없을 때만 원문 제공을 요청한다.

### 26.4 작업 크기를 정하는 기준

작업 단위는 장 번호·파일 수·고정 시간·토큰 잔량 비율이 아니라 **하나의 관찰 가능한 동작 또는 하나의 판별 가능한 의문**이다.

좋은 구현 단위는 성공했을 때 무엇이 달라지는지, 실패를 무엇으로 확인하는지, 의존하는 인터페이스가 무엇인지, 어떻게 복구할지 명확하다. 여러 파일을 고쳐야 해도 하나의 원인–동작–검증 사슬이면 한 작업일 수 있다.

| 너무 크거나 잘못 끊은 단위 | 권장하는 하위 단위 예 |
|---|---|
| 인증 전부 고치기 | 여러 요청의 401이 겹칠 때 갱신은 한 번이고 새 세션은 보존되는 경로 |
| 서비스 워커 작성 완료 | 시작/중간/끝 Range를 올바르게 읽고 기존 영상으로 첫 프레임까지 전달하는 경로 |
| 모든 동영상 형식 지원 | 실제 발견된 컨테이너만 비호환인 한 유형을 무재인코딩 재포장하고 탐색·취소까지 검증 |
| 삭제 기능 구현 | 휴지통 요청의 응답이 끊겨도 원격 상태 재조회로 성공·실패·미확정을 구분 |
| UI 파일만 완성 | 원본/호환/오류/일시정지에서 상시 패널 없이 필요한 하단 동작에 접근 |

연구 작업의 산출물도 허용한다. 예를 들어 “두 구조 중 어느 쪽이 실제 실패 표본을 해결하는가”는 재현 실험과 결정으로 닫을 수 있다. 다만 조사만 반복하면서 구현 진척으로 계산하지 않는다.

한 작업 안에서 계획·구현·검증을 계속 쪼개 재시작해야 한다면 더 작은 검증 단위로 나눈다. 컨텍스트 한 번에 반드시 끝내라는 절대 조건은 두지 않는다. 기능 간 경계를 억지로 끊는 것보다, 중간 상태를 정확히 보존하는 편이 안전한 경우도 있다.

### 26.5 Drive Original에 적용할 단계 지도

아래는 기존 WP ID를 유지하는 재묶음이다. 00·06장의 확정 운영 조건을 적용한다. 하나의 묶음이 반드시 채팅 하나나 커밋 하나라는 뜻은 아니다.

| 묶음 | 연결 WP | 완료 결과 |
|---|---|---|
| A. 기준과 반례 | WP-00, WP-01 | 실행 버전·권한·도구·실패 표본, 최소 진단, 현재 장애 계층이 확인됨 |
| B. 분리 가능한 UI 결함 | WP-02 | 상시 아일랜드·정상 동작 문구 제거와 기존 하단/키보드 제어의 회귀 확인 |
| C. 구조의 최소 연결 검증 | WP-03, 필요한 WP-04/06 실험, WP-08 이관 설계 | 확정된 웹/무료 조건에서 data path와 B-auth 각각 검증, 한 파일 연결·이관 확인 |
| D. 인증·계정 보존 | WP-04, WP-08 | 선택된 구조에서 만료·재연결·계정 변경·기존 기록 보존을 작은 경로별로 검증 |
| E. 실제 쓰기 정확성 | WP-05 | 파일별 원격 결과 확인, 부분 성공, 응답 유실·계정 변경 시 안전성 |
| F. 긴 영상·형식 확대 | WP-06, WP-07 | 기본 원본 경로 유지 상태에서 긴 파일·끝 인덱스·탐색·재포장·이미지 등 실제 필요한 조합 확대 |
| G. 종합 인수·릴리스 | WP-09, WP-10 | 실제 기기·실계정·승인된 테스트 쓰기·성능·보안·배포 후 확인 |

묶음 C에서 모든 인증/미디어 기능을 완성하려 하지 않는다. 최소 후보 실험으로 잘못된 구조를 일찍 기각한다. 이 앱의 후보 origin/OAuth·무료 검증 배포는 01장 범위에 포함돼 있으며, 본인 조작·약관·과금·도구 권한 경계가 남으면 그것만 구체적으로 요청한다. 여기의 묶음 C는 네이티브 아키텍처 C를 뜻하지 않는다.

D의 데이터 이관 조건은 마지막에 덧붙이는 부가 작업이 아니다. OAuth 소유권이나 origin을 바꾸기 전 C에서 먼저 설계하고, 변경과 함께 검증한다.

E와 F의 세부 순서는 인증 인터페이스 안정성과 확인된 실패 원인에 따라 조정할 수 있다. 독립성·승인 범위를 확인한 후에만 병렬화를 고려한다. 실제 iPhone에서 결정적인 경로를 검증할 수 있으면 C~F의 이른 시점에도 검사하여 마지막에 구조 문제를 발견하지 않게 한다.

최종 G만 통합 검사를 하는 구조는 금지한다. 변경한 공통 인터페이스의 호출자는 각 단계에서 통합 검사한다. 새로 발견된 직접 관련 결함은 같은 동작을 완성하는 데 필요한 범위에서 수정하고, 독립 문제는 작업판에 연결한다. 근본 원인을 발견했다면 작업 경계·선행조건을 명시적으로 갱신한다.

### 26.6 한 작업의 실행·종료 루프

1. 복구 기록과 실제 Git 상태를 대조한다. 이전 미커밋 변경을 보존한다.
2. READY 상태의 작업 하나를 고른다. 선행조건·권한·관련 원문을 확인한다.
3. 기대 행동과 실패를 구분할 검증을 확정한다. 기존 결함이면 먼저 재현한다.
4. 최소 필요한 구현을 하고 관련 호출자와 상태 소유자를 함께 점검한다.
5. 집중 테스트와 영향받는 통합 검사를 실행한다. 화면 변경은 실제 렌더링·입력을 확인한다.
6. 실제 diff와 요구를 비교한다. 테스트가 구현의 잘못된 전제를 그대로 되풀이하지 않는지 검토한다.
7. 검증된 코드 상태를 소스 식별자·결과 경로와 연결해 기록하고, 허용된 작업 브랜치에서 리뷰 가능한 커밋을 만든다.
8. 체크포인트를 현행화한다. 승인된 다음 READY 작업이 있으면 진행하며, 필요한 승인·접근 차단만 사용자에게 전달한다.

실제 기기·계정·쓰기 증거가 없으면 해당 검사는 BLOCKED/미검증이다. mock 통과로 바꾸지 않는다. 새 요구 때문에 테스트를 수정할 때는 기존 계약이 왜 바뀌는지 기록하고 새 계약을 더 정확히 검사한다. 실패를 없애기 위한 삭제·완화는 금지한다.

검사 비용은 구분한다. 작은 변경마다 긴 실기기 전체 검사를 반복할 필요는 없지만, 빠른 집중 검사와 경계 통합 검사는 수행한다. 전체 회귀·실환경 인수는 합의된 단계와 릴리스 게이트에서 수행하며, 의존성 변경으로 무효화된 관련 증거는 재검증한다.

### 26.7 컨텍스트 압축·중단에 견디는 복구 계약

#### 26.7.1 압축 전에만 기록하려 하지 않는다

자동 compaction 또는 새 세션 전환을 지원하는 실행 환경에서는 그 기능을 사용할 수 있다. Sol Ultra의 실제 도구·옵션·압축 주기를 추정하지 않는다. 압축 자체를 고장으로 보지 않되, 대화 밖에 구현·검증 상태를 재구성할 근거를 둔다. 원본 규약의 Codex compaction 설명은 이러한 설계의 참고 자료다. [EP01]

에이전트가 정확한 압축 시점·남은 토큰 비율·백그라운드 재개 가능성을 안다고 가정하지 않는다. 중요한 가설 기각, 구조 결정, 코드 변경 묶음, 테스트 완료, 외부 작업 시작/확정, 사용자 권한 변경마다 지속적으로 기록한다.

#### 26.7.2 체크포인트가 알려줘야 하는 것

체크포인트는 일기나 대화 요약이 아니라 재시작 지점이다. 최소한 다음이 들어가야 한다.

- 현재 작업 ID와 연결된 요구·인수 테스트 ID.
- 저장소·브랜치·HEAD, 미커밋 변경의 범위와 소유자.
- 구현 완료·검증 완료·차단 상태의 구분.
- 마지막 실제 검증 결과의 위치, 검증 대상 코드 식별자, mock/실계정/실기기 구분.
- 남은 정확한 실패와 이미 기각한 접근의 짧은 이유/결정 참조.
- 다음 행동 하나와 관찰할 결과.
- 실행 중인 해당 작업 프로세스·결과 파일의 참조 및 외부 쓰기의 미확정 여부.
- 현재 허용/금지 행동과 필요한 다음 승인.

예시 형식이며 실제 작업 결과가 아니다:

```yaml
source:
  branch: null

references:
  specification: Drive-Original_Sol-Ultra_Implementation-Pack_v3.0_2026-09-19.md

  run_path: null

  evidence_level: null

```

민감한 토큰·쿠키·로그인 세션·개인 파일 원문을 복구 문서에 넣지 않는다. 실제 외부 작업 식별자는 승인된 비공개 operation ledger가 소유하고 체크포인트는 그 위치만 가리킨다.

#### 26.7.3 압축 후·새 세션의 재시작 순서

현재 지시와 권한 → 프로젝트 지침/인덱스 → 체크포인트 → 활성 작업/관련 원문 → 실제 Git 상태·diff·필요 소스 → 기록된 증거를 확인한다.

기록과 실제 코드가 다르면 코드를 무조건 기록값으로 되돌리지 않는다. 사용자·다른 작업의 변경 여부를 확인하고 현재 상태를 조정한다. 원문 요구는 코드보다 우선하는 목표이며, Git은 현재 구현의 사실을 알려준다. 둘의 역할을 혼동하지 않는다.

검증된 부분은 근거 없이 다시 작성하지 않는다. 확인되지 않은 결과를 성공으로 채우지도 않는다. 진행 중이던 명령은 결과 파일·현재 프로세스를 먼저 확인한다. 특히 Drive 쓰기·배포·이관은 응답이 안 보인다는 이유로 재실행하지 않고 외부 실제 상태부터 확인한다.

#### 26.7.4 중간 실패 상태의 처리

가능하면 빌드·핵심 검증이 되는 경계에서 끝낸다. 그러나 토큰·시간·연결 중단이 임박했는데 억지로 완료 상태를 꾸미거나 변경을 삭제하지 않는다.

미완성 코드는 작업 브랜치에 보존하고, 빌드 상태·재현 명령·실패·다음 행동을 기록한다. 필요하고 승인된 경우 WIP라고 명시한 체크포인트 커밋을 쓸 수 있지만 통합/배포 가능한 커밋과 구분한다. `git reset --hard`나 `git clean`으로 기존 변경을 지워서 clean을 만들지 않는다.

### 26.8 같은 채팅·새 채팅·병렬 워커의 사용 기준

관련 구현은 기본적으로 같은 총괄 채팅에서 이어간다. 원본 규약이 참고한 공식 장기 작업 지침의 취지도 관련 작업의 맥락 유지와 독립 작업 분리다. 특정 `/goal` 등의 옵션을 Sol Ultra에 있다고 가정하지 않으며, 실제 지원 기능도 권한·인수 기준을 확대하지 않는다. [EP02]

새 컨텍스트가 유용한 경우는 충분히 기록된 단계가 닫힌 뒤 다른 독립 영역을 다루거나, 가설·로그가 쌓여 같은 분석을 반복하거나, 기존 구현의 설명에 영향받지 않는 리뷰가 필요한 때다. 압축 횟수만을 기준으로 강제 교체하지 않는다.

| 방식 | 기본 판단 |
|---|---|
| 주 워커 1개로 관련 변경 순차 통합 | 기본 |
| 독립 공식문서 조사·소스 탐색·정해진 SHA 리뷰 | 필요할 때 보조 워커 |
| 인터페이스가 확정된 독립 모듈 구현 | 충돌·통합 비용을 확인한 뒤 제한적 병렬 |
| 여러 워커가 같은 app.js를 각자 수정 | 피함 |
| 공유 인터페이스·OAuth 이관·배포를 독립 워커들이 각자 결정 | 금지 |

Codex 공식 문서는 읽기 중심 작업부터 병렬화하고 쓰기 중심 작업의 충돌에 주의하도록 안내한다. 병렬 워커는 토큰을 추가 소비하므로 사용량 부족을 해결하는 기본 수단이 아니다. 연구 결과도 작업의 분해 가능성과 순차 의존성에 따라 다중 에이전트의 효과가 달라짐을 보여 준다. [EP05][EP06]

worktree는 파일 편집을 격리하는 수단이지 의미적 충돌을 해결하는 수단이 아니다. 사용 시 현재 기반 SHA·소유 파일·인터페이스·통합 담당자를 지정한다. 다른 워커와 같은 테스트 서버·브라우저 프로필·포트·live 데이터에 동시 쓰기를 하지 않는다. [EP08]

### 26.9 독립 검토와 완료 상태

핵심 단계에서는 가능하면 새 컨텍스트의 검토자에게 사용자 요구, 확정된 계약, 고정된 소스 SHA/diff, 테스트·증거만 먼저 제공한다. 구현자의 장황한 정당화보다 실제 요구와 반례를 기준으로 검토하게 한다.

동일 모델의 두 답변이 일치한 것은 독립적인 실제 증거가 아니다. 검토자는 재현할 수 있는 반례, 호출자 불일치, 미검증 경로 또는 구체적인 테스트 누락을 반환해야 한다. 없으면 없는대로 말한다. 검토자가 반드시 버그를 만들어내도록 요구하지 않는다.

작업 상태의 권장 의미:

- `READY`: 선행 계약·권한·검증 방법이 갖춰져 시작할 수 있음.
- `IN_PROGRESS`: 구현/검증 중. 성공 단정 금지.
- `IMPLEMENTED_LOCAL`: 로컬 구현과 명시된 검사는 통과했지만 실제 인수가 남음.
- `BLOCKED`: 명시된 접근·승인·외부 조건 때문에 특정 검사가 진행되지 못함.
- `ACCEPTED`: 해당 작업에 필요한 인수 증거까지 확보됨.

테스트 자체의 상태값은 본 문서 20장을 따른다. 별도 상태판을 또 만들지 않고 활성 실행계획에 필요한 구분만 반영한다. 부분 구현 완료와 프로젝트 최종 인수 완료를 분리한다.


### 26.10 사용자가 단계 보고에서 확인할 다섯 문장

진행률이나 커밋 수보다 다음 다섯 질문에 대한 답을 확인한다.

1. 이번 단계로 실제 무엇이 달라졌는가?
2. 어떤 반례/실패가 이제 통과하는가?
3. 어느 코드·환경에서 무엇을 실제 검증했는가?
4. 아직 무엇이 구현 전·미검증·차단 상태인가?
5. 다음 행동은 무엇이고 어떤 승인/정보가 정말 필요한가?

반복적인 조사, 같은 파일 재작성, 실패 테스트 완화, 큰 미커밋 변경 누적,
각 모듈만 통과하고 전체는 안 되는 상태, 외부 결과 없는 성공 선언이 보이면
작업 속도를 올리기보다 현재 작업 경계·전제·검증 기준부터 수정한다.


### 26.11 고정 소스·증거·체크포인트의 연결

- 검증 대상 코드가 미커밋이면 기준 HEAD와 diff/트리 식별·작업 파일 범위를 남긴다. 이후 커밋을 만들면 같은 검증 대상인지 대조한다.
- 기능 코드를 바꾸면 영향받는 이전 증거의 유효성을 재평가한다. 문서만 바뀐 경우 런타임 바이트와 새 문서 커밋을 구분한다.
- 체크포인트에 **자기 자신을 담은 최종 HEAD를 반복 갱신해 무한 문서 커밋**을 만들지 않는다. 마지막 검증 대상 코드 SHA와 현재 `git status/log` 재조회 규칙으로 충분하다.
- 성공 run을 덮어쓰기보다 새 run을 연결하고, 실패·fixture 결함·재현 성공을 구분한다. 전체 검사와 선택 검사, 현재 기기와 이전 기기를 혼동하지 않는다.
- 테스트를 끝내지 못한 WIP는 빌드/실패/다음 행동과 함께 보존한다. clean 상태를 만들기 위해 사용자 작업을 지우지 않는다.
- 접근 권한이 없던 `G:`를 무한 재시도하지 않는다. 거부 이유·필요 승인과 실행 가능한 다른 작업을 기록한다.
- 이미 전송된 Drive 작업·후보 배포·OAuth 설정 변경의 응답이 사라지면 외부 현재 상태를 먼저 조회한다. 같은 동작을 다시 보내는 것은 복구가 아니다.

### 26.12 새 세션의 재개·독립 검토 템플릿

**재개:** 현재 사용자 범위 → 00·01장 → goal/CHECKPOINT → 활성 작업 원문 → 실제 branch/status/diff → 마지막 증거 → 남은 행동 순으로 읽는다. 기존 구현을 기억이 없다는 이유로 재작성하지 않는다. 승인된 READY가 있으면 계속한다.

**고정 SHA 검토:** 명세·계약·고정 diff와 실제 테스트를 근거로 요구 위반, 상태 소유권 충돌, 거짓 성공, 중요한 미검증 경로를 찾는다. 발견마다 위치·실패 조건·사용자 영향·재현 또는 반증 방법을 제시한다. 확인되지 않은 의심과 재현 결함을 구분하고, 반드시 결함을 만들어낼 필요는 없다. 검토 역할에서는 제품 소스·실제 원본·운영 배포를 변경하지 않는다.

**중지 조건:** 사용자가 중지했거나, 남은 중요 작업이 모두 실제 접근·본인 조작·예산·운영 승인에 막혔거나, 고정된 인수 가능한 후보가 준비된 때다. 첫 계획·첫 trace·첫 READY 완료 자체는 중지 조건이 아니다. 실행 환경이 종료돼야 하면 체크포인트를 남기고 현재 상태를 정직하게 보고한다. 지원되지 않는 백그라운드 작업이나 자동 재개를 약속하지 않는다.
